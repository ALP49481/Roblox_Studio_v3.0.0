Dificuldade 3/5 · intermediária

Organize para mudar sem quebrar — e prove cada mudança.

Você dividirá a loja segura em responsabilidades pequenas, construirá uma porta com estados explícitos, investigará defeitos com evidências e criará uma rotina de versão e revisão. Arquitetura não significa mais arquivos: significa limites claros.

  • Ponto de partida: tipagem Luau, eventos, cliente-servidor, validação e loja segura
  • Projeto: concluir a Loja segura com módulos, ciclo de vida e matriz de regressão
  • Limite consciente: o inventário continua em memória; persistência e DataStore começam somente no Módulo 7
O teste guia a divisão

Se uma regra pode ser testada sem Player, GUI ou rede, mantenha-a pura. Se precisa da engine, isole a borda. Assim um erro aponta para uma região menor.

Capítulo 6.1

ModuleScript, configuração, estado e contratos tipados

Extraia regras da loja sem perder a autoridade do servidor.

Objetivos, pré-requisitos e vocabulário

Pré-requisitos: 2.7–2.9 e 5.5. Ao terminar, você distinguirá configuração de estado, projetará uma API pública pequena, usará tipos exportados e explicará o cache de require().

API pública
Funções e tipos que o módulo oferece aos consumidores.
Configuração
Regra definida pelo desenvolvedor, como preço e limite.
Estado
Valor que muda durante a sessão, como saldo e quantidade possuída.
Contrato tipado
Descrição verificável das entradas e saídas de uma função.
Cache
Reutilização do valor retornado pelo primeiro require no mesmo ambiente.
Função pura
Função cujo resultado depende apenas dos argumentos e não altera o mundo.

Um módulo não é automaticamente uma boa arquitetura

require(moduleScript) executa o ModuleScript uma vez e devolve seu valor. Outro require() no mesmo ambiente recebe a mesma referência; servidor e cliente mantêm caches separados. Por isso, alterar uma tabela retornada pode afetar todos os consumidores daquele lado.

Compartilhado não significa secreto

ModuleScript em ReplicatedStorage pode ser lido pelo cliente. Preços podem ser públicos, mas o servidor ainda usa sua própria cópia e decide a compra. Nunca coloque chave, token ou lógica confidencial em conteúdo replicado.

Dependência circular

Se A exige B e B exige A, o carregamento falha como módulo requerido recursivamente. Faça o fluxo apontar numa direção: o servidor de entrada conhece Shop; Shop conhece catálogo e economia; esses módulos não conhecem o servidor de entrada.

ItemCatalog.luauModuleScript · ServerScriptService/Loja · servidor · no primeiro require
--!strict
export type ItemDefinition = {
	id: string,
	displayName: string,
	price: number,
	maxOwned: number,
	templateName: string,
}

local definitions: {[string]: ItemDefinition} = {
	lanterna_dourada = table.freeze({
		id = "lanterna_dourada",
		displayName = "Lanterna dourada",
		price = 25,
		maxOwned = 1,
		templateName = "LanternaDourada",
	}),
}

local ItemCatalog = {}

function ItemCatalog.get(itemId: string): ItemDefinition?
	return definitions[itemId]
end

function ItemCatalog.list(): {ItemDefinition}
	local result = {}
	for _, definition in definitions do
		table.insert(result, definition)
	end
	return result
end

return table.freeze(ItemCatalog)

O tipo exportado documenta cada item. As definições e a API são congeladas para impedir alterações acidentais; list() devolve uma lista nova. Congelamento melhora disciplina, não transforma ReplicatedStorage em segredo.

  1. Em Economy, deixe apenas cálculos e alterações numéricas explícitas.
Economy.luauModuleScript · ServerScriptService/Loja · servidor · no primeiro require
--!strict
local Economy = {}

function Economy.canAfford(balance: number, price: number): boolean
	return math.isfinite(balance)
		and math.isfinite(price)
		and balance >= 0
		and price >= 0
		and balance >= price
end

function Economy.debit(balance: number, price: number): number?
	if not Economy.canAfford(balance, price) then
		return nil
	end
	return balance - price
end

return table.freeze(Economy)

Essas funções não procuram Instances nem alteram IntValue. Isso permite testar saldo exato e valores inválidos sem abrir uma sessão multiplayer.

  1. Em Shop, componha catálogo e economia. O estado de inventário é recebido como argumento, não escondido dentro do catálogo.
Shop.luauModuleScript · ServerScriptService/Loja · servidor · chamado pelo bootstrap
--!strict
local ItemCatalog = require(script.Parent.ItemCatalog)
local Economy = require(script.Parent.Economy)

export type Inventory = {[string]: number}
export type Result = {ok: boolean, message: string, newBalance: number?}

local Shop = {}

function Shop.evaluate(
	balance: number,
	inventory: Inventory,
	itemId: string
): Result
	local item = ItemCatalog.get(itemId)
	if not item then
		return {ok = false, message = "Item desconhecido.", newBalance = nil}
	end

	local owned = inventory[itemId] or 0
	if owned >= item.maxOwned then
		return {ok = false, message = "Limite do item alcançado.", newBalance = nil}
	end

	local newBalance = Economy.debit(balance, item.price)
	if newBalance == nil then
		return {ok = false, message = "Moedas insuficientes.", newBalance = nil}
	end

	return {ok = true, message = "Compra aprovada.", newBalance = newBalance}
end

return table.freeze(Shop)

evaluate() calcula uma decisão; não concede a Tool. O bootstrap de 5.5 continua validando remote, requestId, frequência, vida e distância. Depois chama Shop.evaluate() e, se ok, atualiza saldo/inventário e clona o molde sem yield.

  1. No Script ServidorDaLoja, remova CATALOGO e as comparações extraídas. Adicione local Shop = require(script.Parent.Loja.Shop) no topo.
  2. No ponto já validado da transação, chame local decision = Shop.evaluate(moedas.Value, inventarios[player], itemId). Se não aprovado, devolva a mensagem; se aprovado, use decision.newBalance após confirmar que não é nil.
  3. Use Script Analysis: não deve haver aviso de tipo. Use Play perto do balcão e repita os testes de 5.5.

Resultado esperado: comportamento externo idêntico ao anterior, com regras puras isoladas. Se require falhar, confira nomes, parentes e ausência de ciclo. Para desfazer, abra a versão salva ou restaure a cópia local, nunca improvise metade da arquitetura antiga com metade da nova.

Capítulo 6.2

Composição, ciclo de vida e máquinas de estado

Uma porta parece simples até receber dois comandos ao mesmo tempo. Organize mudanças em estados válidos e dê ao sistema começo, execução e encerramento claros.

Antes de começar

Você aprenderá: composição, dependências explícitas, estados, transições e o ciclo init → start → destroy. Pré-requisito: 6.1, eventos de 3.1 e CFrame de 4.2.

Composição
Construir um sistema juntando partes menores com responsabilidades diferentes.
Dependência
Serviço ou objeto de que um módulo precisa para trabalhar.
Estado
Situação atual do sistema, como Closed ou Open.
Transição
Mudança autorizada de um estado para outro.
Ciclo de vida
Fases de preparação, funcionamento e limpeza de um sistema.

Um modelo mental para sistemas que mudam

Imagine um semáforo. Ele não pula livremente para qualquer cor; há uma sequência permitida. Uma máquina de estados registra a situação atual e aceita somente mudanças válidas. Isso evita que a porta tente abrir, fechar e abrir outra vez no mesmo instante.

Closed→Opening→Open→Closing→Closed

O controlador receberá o TweenService pelo construtor. Essa injeção de dependência torna claro o que ele usa e facilita trocar uma dependência em testes. Não é preciso criar uma hierarquia de classes para tudo: composição costuma ser mais direta para sistemas de jogo.

Regra de segurança

Esta porta reage a um ProximityPrompt no servidor. Se um dia um LocalScript solicitar a abertura por RemoteEvent, o servidor ainda deverá confirmar permissão, distância, estado e frequência.

Prática guiada: uma porta com estados válidos

Projeto aberto: crie uma cópia local da experiência da loja segura. Assim, a porta não interfere no projeto que já funciona.

  1. No Explorer, crie Workspace → Arquitetura → PortaArquitetada, nesta ordem: Folder, Model.
  2. Dentro do Model, crie duas Parts: Painel e DestinoAberto. Em ambas, marque Anchored = true. No destino, use Transparency = 1 e CanCollide = false; mova-o alguns studs para o lado.
  3. Dentro de Painel, crie um ProximityPrompt chamado AlternarPorta. Defina ActionText = Abrir ou fechar, ObjectText = Porta e HoldDuration = 0.
  4. Crie ServerScriptService → Arquitetura → DoorController como ModuleScript e substitua todo o conteúdo.

game → ServerScriptService → Arquitetura → DoorController

DoorController.luauModuleScript · ServerScriptService/Arquitetura · servidor · carregado pelo bootstrap
--!strict
local DoorController = {}
DoorController.__index = DoorController

export type DoorState = "Closed" | "Opening" | "Open" | "Closing"

type Dependencies = {
	TweenService: typeof(game:GetService("TweenService")),
}

type ControllerData = {
	model: Model,
	dependencies: Dependencies,
	state: DoorState,
	panel: BasePart?,
	prompt: ProximityPrompt?,
	closedCFrame: CFrame?,
	openCFrame: CFrame?,
	promptConnection: RBXScriptConnection?,
	tweenConnection: RBXScriptConnection?,
	activeTween: Tween?,
	destroyed: boolean,
}

export type Controller = typeof(setmetatable({} :: ControllerData, DoorController))

local VALID_TRANSITIONS: {[DoorState]: {[DoorState]: boolean}} = {
	Closed = {Opening = true},
	Opening = {Open = true},
	Open = {Closing = true},
	Closing = {Closed = true},
}

function DoorController.new(model: Model, dependencies: Dependencies): Controller
	local self = setmetatable({
		model = model,
		dependencies = dependencies,
		state = "Closed" :: DoorState,
		panel = nil,
		prompt = nil,
		closedCFrame = nil,
		openCFrame = nil,
		promptConnection = nil,
		tweenConnection = nil,
		activeTween = nil,
		destroyed = false,
	}, DoorController)
	return self
end

function DoorController._transition(self: Controller, nextState: DoorState): boolean
	if not VALID_TRANSITIONS[self.state][nextState] then
		warn(`Transição inválida: {self.state} → {nextState}`)
		return false
	end
	self.state = nextState
	self.model:SetAttribute("DoorState", nextState)
	return true
end

function DoorController.init(self: Controller)
	assert(not self.destroyed, "Controlador destruído não pode ser iniciado")
	local panel = self.model:FindFirstChild("Painel")
	local destination = self.model:FindFirstChild("DestinoAberto")
	assert(panel and panel:IsA("BasePart"), "Painel BasePart ausente")
	assert(destination and destination:IsA("BasePart"), "DestinoAberto BasePart ausente")
	local prompt = panel:FindFirstChild("AlternarPorta")
	assert(prompt and prompt:IsA("ProximityPrompt"), "ProximityPrompt ausente")

	self.panel = panel
	self.prompt = prompt
	self.closedCFrame = panel.CFrame
	self.openCFrame = destination.CFrame
	self.model:SetAttribute("DoorState", self.state)
end

function DoorController._move(
	self: Controller,
	target: CFrame,
	finalState: DoorState
)
	local panel = assert(self.panel, "init() precisa ser chamado primeiro")
	local tween = self.dependencies.TweenService:Create(
		panel,
		TweenInfo.new(0.8, Enum.EasingStyle.Quad, Enum.EasingDirection.Out),
		{CFrame = target}
	)
	self.activeTween = tween
	self.tweenConnection = tween.Completed:Connect(function(playbackState)
		if tween ~= self.activeTween then
			return
		end
		if self.tweenConnection then
			self.tweenConnection:Disconnect()
			self.tweenConnection = nil
		end
		self.activeTween = nil
		if playbackState == Enum.PlaybackState.Completed then
			self:_transition(finalState)
		end
	end)
	tween:Play()
end

function DoorController.toggle(self: Controller)
	if self.destroyed then
		return
	end
	if self.state == "Closed" and self:_transition("Opening") then
		self:_move(assert(self.openCFrame), "Open")
	elseif self.state == "Open" and self:_transition("Closing") then
		self:_move(assert(self.closedCFrame), "Closed")
	end
end

function DoorController.start(self: Controller)
	assert(self.prompt, "init() precisa ser chamado antes de start()")
	assert(not self.promptConnection, "start() não pode ser chamado duas vezes")
	self.promptConnection = self.prompt.Triggered:Connect(function()
		self:toggle()
	end)
end

function DoorController.destroy(self: Controller)
	if self.destroyed then
		return
	end
	self.destroyed = true
	if self.promptConnection then
		self.promptConnection:Disconnect()
		self.promptConnection = nil
	end
	if self.tweenConnection then
		self.tweenConnection:Disconnect()
		self.tweenConnection = nil
	end
	if self.activeTween then
		self.activeTween:Cancel()
		self.activeTween = nil
	end
end

return table.freeze(DoorController)

new() guarda dados, init() verifica objetos, start() conecta o evento e destroy() desfaz conexões e animações. Durante Opening ou Closing, novos acionamentos são ignorados. O atributo DoorState permite observar o estado em Properties.

Fácil

Adicione um atributo LastTransitionAt com workspace:GetServerTimeNow() após uma transição válida.

Intermediário

Desafiador

Pequeno projeto: a arquitetura da loja ganha uma porta reutilizável, com dependências visíveis e limpeza das conexões.

  • Reconheço configuração, estado e dependência.
  • Sei por que transições inválidas são recusadas.
  • Sei a responsabilidade de init, start e destroy.
  • Não criei dependência circular.
  • Consigo observar o estado no Studio.

Desafiador: mantenha uma lista de Models, crie um controlador por elemento e guarde-os em uma tabela para chamar destroy() em todos. Não use um estado global compartilhado.

Capítulo 6.3

Depuração, testes e proteção contra regressões

Um erro deixa de ser um mistério quando você consegue reproduzi-lo, observar evidências e confirmar a correção.

Antes de começar

Você aprenderá: diferença entre erro de sintaxe, execução e lógica; leitura de stack trace; breakpoints; Watch, Call Stack e testes de regressão. Pré-requisitos: Módulo 5 e capítulos 6.1–6.2.

Bug
Comportamento diferente do que foi especificado.
Reprodução
Sequência mínima e repetível que faz o problema aparecer.
Stack trace
Lista de chamadas que mostra o caminho até um erro.
Breakpoint
Ponto onde o depurador pausa a execução para inspecionar valores.
Regressão
Falha reaparecida ou criada ao modificar algo que funcionava.
Caso de teste
Entrada, ação e resultado esperado definidos antecipadamente.

Investigue, não adivinhe

Um fluxo confiável tem seis passos: descrever o esperado, reproduzir, reduzir o caso, observar evidências, corrigir a causa e retestar. Alterar várias linhas ao acaso destrói pistas.

Esperado→Reproduzir→Reduzir→Observar→Corrigir→Retestar

O Output informa mensagem, script e linha. A Call Stack mostra quem chamou quem. Watch acompanha expressões enquanto a sessão está pausada. Um logpoint registra informação sem interromper; um breakpoint comum pausa. Escolha o contexto correto — servidor ou cliente — porque cada lado possui execução e memória próprias.

Erro comum

Colocar todo o código dentro de pcall() para “parar mensagens” esconde a causa e torna o estado imprevisível. Nesta prática, pcall isola casos de teste; uma falha ainda é exibida e o conjunto termina com erro.

Prática guiada: três falhas, cinco testes

Projeto aberto: a cópia da loja modular feita em 6.1. Salve uma versão antes de inserir falhas intencionais.

Parte A — diagnostique três classes de erro

  1. Tipo/sintaxe: em uma cópia de ItemCatalog, troque temporariamente price = 25 por price = "25". Abra Script Analysis. O contrato deve indicar que string não é number. Desfaça a linha.
  2. Execução: troque temporariamente o nome MoldeLanterna procurado pelo servidor por MoldeLanternaa. Execute a compra. Leia a mensagem e clique no link da linha no Output. Corrija o nome.
  3. Lógica: em Economy.canAfford(), troque balance >= price por balance > price. Um saldo exatamente igual ao preço será recusado sem erro vermelho. Restaure >=.
  4. Adicione um breakpoint na primeira linha de Shop.evaluate(). Use Play e compre. No painel Watch, observe balance, itemId e inventory[itemId]; na Call Stack, encontre o Script servidor que chamou o módulo. Continue a execução e remova o breakpoint.

Resultado esperado: cada falha possui evidência diferente. Se o breakpoint não for alcançado, confirme que ele está no contexto Server e que a ação realmente chegou ao servidor.

Parte B — transforme regras em testes repetíveis

  1. Crie um Script desabilitado chamado TestadorDaLoja em ServerScriptService → Loja. Ele deve existir apenas na cópia de desenvolvimento; não publique um testador que force falha no servidor de produção.
  2. Cole o código, marque Enabled = true e use Run. Leia cada PASS no Output.

game → ServerScriptService → Loja → TestadorDaLoja

TestadorDaLoja.server.luauScript · ServerScriptService/Loja · servidor · somente em sessão de desenvolvimento
--!strict
local ItemCatalog = require(script.Parent.ItemCatalog)
local Economy = require(script.Parent.Economy)
local Shop = require(script.Parent.Shop)

type TestCase = {
	name: string,
	run: () -> (),
}

local tests: {TestCase} = {}

local function addTest(name: string, run: () -> ())
	table.insert(tests, {name = name, run = run})
end

addTest("saldo exato compra", function()
	assert(Economy.canAfford(25, 25), "25 deveria pagar 25")
	assert(Economy.debit(25, 25) == 0, "saldo final deveria ser zero")
end)

addTest("saldo insuficiente não debita", function()
	assert(Economy.debit(24, 25) == nil, "débito deveria ser recusado")
end)

addTest("item desconhecido não existe", function()
	assert(ItemCatalog.get("nao_existe") == nil, "id inválido foi encontrado")
end)

addTest("loja aprova caso feliz", function()
	local result = Shop.evaluate(30, {}, "lanterna_dourada")
	assert(result.ok, result.message)
	assert(result.newBalance == 5, "saldo final incorreto")
end)

addTest("loja respeita limite", function()
	local result = Shop.evaluate(100, {lanterna_dourada = 1}, "lanterna_dourada")
	assert(not result.ok, "segunda lanterna deveria ser recusada")
	assert(result.newBalance == nil, "recusa não deve criar saldo novo")
end)

local failures = 0
for _, testCase in tests do
	local ok, message = pcall(testCase.run)
	if ok then
		print(`[PASS] {testCase.name}`)
	else
		failures += 1
		warn(`[FAIL] {testCase.name}: {message}`)
	end
end

assert(failures == 0, `{failures} teste(s) falharam`)
print(`Todos os {#tests} testes passaram.`)

Cada função testa uma regra pequena. O pcall permite executar os casos restantes depois de um assert, mas a asserção final mantém a falha visível.

  1. Reintroduza apenas o bug >. Use Run: o primeiro teste deve falhar e os demais devem continuar. Corrija e execute novamente.
  2. Ao terminar, marque Enabled = false. Use Play Solo para o fluxo comum; depois use Test → Server & Clients com dois clientes e encerre com End Session.
  3. No Device Emulator, confira a interface da loja nas resoluções usadas no Módulo 4. No Controller Emulator, repita a navegação. Para testar condições piores, use Network Simulation e nunca o controle legado de atraso de replicação em implementações novas.

Capítulo 6.4

Versões, colaboração, Packages e arquivos locais

Manutenção começa antes do problema: uma mudança pequena, revisável e recuperável é muito mais segura que uma grande alteração sem histórico.

Antes de começar

Você aprenderá: diferença entre salvar, publicar, versionar e colaborar; uso cuidadoso de Packages; Script Sync; revisão e rollback. Pré-requisito: loja testada do 6.3.

Versão
Registro identificado do estado do projeto em determinado momento.
Commit
Registro local de um conjunto coerente de mudanças no controle de versão.
Diff
Comparação que mostra linhas adicionadas, removidas ou modificadas.
Package
Conjunto reutilizável de Instances com versões e atualizações próprias.
Script Sync
Recurso do Studio que sincroniza scripts selecionados com arquivos locais.
Rollback
Retorno planejado a um estado conhecido como estável.

Quatro ações que não significam a mesma coisa

AçãoO que fazO que não garante
Salvar localmenteGrava um arquivo no computadorBackup remoto ou publicação
Save to RobloxCria/atualiza uma versão na nuvemQue o público já recebeu a versão
Publish to RobloxDisponibiliza a versão publicada da experiênciaQue não existam bugs
CommitRegistra mudanças nos arquivos sob controle de versãoSalvar partes do projeto que não foram sincronizadas

Um fluxo seguro liga essas ações: mudança pequena → revisão do diff → testes → versão com nota → publicação deliberada → monitoramento. Restaurar uma versão no Creator Dashboard cria uma nova versão, mas não a publica automaticamente.

Permissão mínima

Dê acesso de edição somente a quem precisa. Colaboradores podem ter permissões diferentes, e os requisitos de idade/conta para colaboração devem ser conferidos na documentação atual. Nunca coloque tokens, senhas ou chaves dentro de scripts, commits ou Packages.

Prática guiada: torne a loja recuperável

Projeto aberto: a experiência de desenvolvimento da loja, com todos os testes do 6.3 aprovados. Não pratique restauração diretamente na experiência pública.

Parte A — marque um ponto estável

  1. Execute os cinco testes e a matriz mínima: compra comum, recusa e dois clientes.
  2. Use File → Save to Roblox. Quando disponível, escreva uma nota objetiva como M6: loja modular com testes aprovados.
  3. No Creator Dashboard, abra a experiência, o place e Version History. Localize a versão pela data e pela nota. Não restaure ainda.

Parte B — experimente um Package com cautela

  1. Na cópia de desenvolvimento, selecione Workspace → Arquitetura → PortaArquitetada e use a opção de converter/publicar como Package. Defina proprietário e permissões conscientemente.
  2. Faça uma alteração visual pequena, publique a atualização do Package e aplique-a primeiro em uma cópia de teste. Ative atualização automática somente quando a compatibilidade tiver sido comprovada.
  3. Antes de inserir Package de terceiros, salve a experiência e inspecione todos os descendentes, especialmente Scripts. Remover PackageLink transforma a cópia em objetos comuns e encerra o comportamento de Package.
Atenção

Um Package não é automaticamente confiável. Código malicioso pode vir dentro de um modelo. Origem, conteúdo, permissões e atualizações precisam de revisão.

Parte C — sincronize scripts com arquivos locais

  1. No Explorer, clique com o botão direito em ServerScriptService → Loja e escolha Sync to…. Selecione uma pasta local dedicada, como roblox-aprendizado/src/Loja.
  2. Confirme os nomes: ItemCatalog.luau, Economy.luau e Shop.luau representam ModuleScripts; um Script servidor usa o sufixo .server.luau. Nomes duplicados ou inválidos impedem a sincronização.
  3. Faça uma cópia de segurança antes da primeira sincronização. Tags e Attributes não são representados pelos arquivos de script e podem ser ignorados, com risco de perda se você presumir o contrário. O depurador do Studio também não é controlado pelo editor externo.

Para sincronizar um projeto inteiro e sua hierarquia, a documentação cita ferramentas externas como Rojo. Essa é uma opção futura, não um requisito deste capítulo.

Parte D — registre uma mudança local

Se Git estiver instalado, abra um terminal dentro da pasta sincronizada. Cada comando abaixo é executado separadamente. Não copie arquivos secretos para essa pasta.

Uma restauração real cria uma versão nova; publique somente depois da confirmação. Se Team Create estiver ativo, desative-o antes de reverter, pois edições ativas podem sobrescrever o retorno.

Resultado esperado: você consegue provar qual linha mudou, qual teste protegeu a mudança e qual versão recuperaria. Para desfazer a prática, use sua cópia local ou a versão estável identificada; não apague o histórico.

Glossário e referências do Módulo 6

Bootstrap

Script pequeno que reúne dependências, cria controladores e inicia o sistema.

Contrato

Formato e comportamento que uma parte promete oferecer às demais.

Função pura

Função cujo resultado depende apenas das entradas e que não altera estado externo.

Idempotência

Propriedade de repetir uma solicitação sem repetir seu efeito importante.

Máquina de estados

Modelo que enumera estados e transições permitidas.

Regressão

Falha introduzida ou reintroduzida por uma mudança.

Dificuldade 2–3/5 · intermediária inicial

Do personagem na tela a controles que funcionam em qualquer dispositivo.

Você ligará o mundo 3D a jogadores reais, separará responsabilidades entre servidor e cliente, construirá uma lanterna e criará o primeiro HUD adaptável. A ordem é deliberada: touch só aparece depois que botões de interface forem ensinados.

  • Ponto de partida: eventos, Instances, atributos, Vector3 e CFrame do Módulo 3
  • Projetos: concluir Obstáculo com eventos; iniciar e concluir Ferramenta utilizável; iniciar e concluir Percurso com checkpoint e interface
  • Limite consciente: o cliente pede e apresenta; moedas, dano, itens e progresso importante serão validados por remotes no Módulo 5
Uma regra nova, sem mistério

O dispositivo do jogador controla sua câmera, sua interface e seus inputs, mas pode ser modificado. Por isso, efeitos apenas visuais podem ficar no cliente; resultados importantes pertencem ao servidor. Neste módulo você aprende a fronteira. A comunicação por remotes vem no próximo.

Capítulo 4.1

Player, Character, Humanoid e respawn

Separe a identidade duradoura da sessão do corpo que pode morrer e ser recriado.

O que você vai dominar

Pré-requisitos: 3.1 e 3.2. Ao terminar, você observará entrada, personagem, morte e respawn; encontrará o jogador a partir de uma peça; evitará conexões duplicadas; aplicará dano com cooldown por jogador; e restaurará um checkpoint válido durante a sessão.

Player
A identidade do usuário dentro daquela sessão.
Character
Model que representa o corpo do jogador no mundo 3D.
Humanoid
Objeto do Character que reúne saúde, movimento e estado de morte.
Respawn
Criação de um novo Character depois da morte ou recarga.
HumanoidRootPart
Peça central usada como referência de posição do personagem.
Sessão
Período em que um servidor está executando; termina quando ele fecha.

Dois ciclos de vida, não um

Player entraidentidade da sessão
→
Character nascecorpo recriável
→
Humanoid morreCharacter é trocado
→
Player continuaaté sair do servidor

Uma conexão em PlayerAdded deve ser criada uma vez. Dentro dela, CharacterAdded prepara cada corpo novo. Conectar CharacterAdded novamente a cada respawn duplicaria trabalho; conectar Humanoid.Died uma vez por Character é correto porque aquele Humanoid será destruído com o corpo.

ObservadorDeJogadores.server.luauScript · ServerScriptService · servidor
local Players = game:GetService("Players")

local contagemDePersonagens = {}
local ultimoCharacterPreparado = {}

local function prepararPersonagem(player, character)
	if ultimoCharacterPreparado[player] == character then
		return
	end
	ultimoCharacterPreparado[player] = character

	contagemDePersonagens[player] = (contagemDePersonagens[player] or 0) + 1
	local numero = contagemDePersonagens[player]
	local humanoid = character:WaitForChild("Humanoid")

	print(player.Name, "recebeu o Character número", numero)

	humanoid.Died:Connect(function()
		print(player.Name, "morreu com o Character número", numero)
	end)
end

local function prepararPlayer(player)
	contagemDePersonagens[player] = 0

	player.CharacterAdded:Connect(function(character)
		prepararPersonagem(player, character)
	end)

	if player.Character then
		prepararPersonagem(player, player.Character)
	end
end

Players.PlayerRemoving:Connect(function(player)
	contagemDePersonagens[player] = nil
	ultimoCharacterPreparado[player] = nil
	print(player.Name, "saiu; estado de sessão removido.")
end)

for _, player in Players:GetPlayers() do
	prepararPlayer(player)
end

Players.PlayerAdded:Connect(prepararPlayer)

contagemDePersonagens usa o Player como chave. O laço inicial cobre jogadores que já existiam quando o Script começou; PlayerAdded cobre os próximos. A verificação de player.Character cobre um corpo já criado. Nenhuma dessas três proteções deve chamar a preparação duas vezes em um início normal.

  1. No menu do teste, use Reset Character dez vezes, aguardando o novo corpo entre tentativas.
  2. Espere números 1 a 11, uma linha de nascimento e uma de morte por corpo anterior. Se um número pular ou repetir, procure outra cópia do Script.
  3. Use Stop. A tabela desaparece com o servidor; isso é estado de sessão, não salvamento.

Para reiniciar: Stop, apague cópias acidentais do Script e execute novamente. Se Humanoid nunca aparecer, confirme que o template de personagem padrão está ativo.

Prática guiada · Projetos 3 e 5

Finalize o obstáculo e crie um checkpoint de sessão

  1. Em game → Workspace → Ambiente → PrimeiraSala → Interacoes, confirme a Part ObstaculoEvento. Defina Anchored true, CanTouch true e uma cor de perigo.
  2. Na mesma pasta, crie as Parts InicioPercurso e Checkpoint1, ambas Anchored. Posicione InicioPercurso no começo e Checkpoint1 depois do obstáculo.
  3. Crie SistemaDePercurso em ServerScriptService, RunContext Server.
SistemaDePercurso.server.luauScript · ServerScriptService · servidor
local Players = game:GetService("Players")
local interacoes = workspace.Ambiente.PrimeiraSala.Interacoes
local obstaculo = interacoes.ObstaculoEvento
local inicio = interacoes.InicioPercurso
local checkpoint1 = interacoes.Checkpoint1

local DANO = 20
local TEMPO_ENTRE_DANOS = 1
local checkpointsPorPlayer = {}
local emCooldown = {}
local ultimoCharacterRestaurado = {}

local function encontrarPlayerEHumanoid(outraParte)
	local character = outraParte:FindFirstAncestorOfClass("Model")
	if not character then
		return nil, nil
	end

	local player = Players:GetPlayerFromCharacter(character)
	local humanoid = character:FindFirstChildOfClass("Humanoid")
	return player, humanoid
end

local function restaurarCheckpoint(player, character)
	if ultimoCharacterRestaurado[player] == character then
		return
	end
	ultimoCharacterRestaurado[player] = character

	local destino = checkpointsPorPlayer[player] or inicio
	character:WaitForChild("HumanoidRootPart")
	character:PivotTo(destino.CFrame + Vector3.new(0, 3, 0))
end

local function prepararPlayer(player)
	checkpointsPorPlayer[player] = inicio
	player:SetAttribute("CheckpointAtual", "Início")

	player.CharacterAdded:Connect(function(character)
		restaurarCheckpoint(player, character)
	end)

	if player.Character then
		restaurarCheckpoint(player, player.Character)
	end
end

obstaculo.Touched:Connect(function(outraParte)
	local player, humanoid = encontrarPlayerEHumanoid(outraParte)
	if not player or not humanoid or humanoid.Health <= 0 or emCooldown[player] then
		return
	end

	emCooldown[player] = true
	humanoid:TakeDamage(DANO)
	task.delay(TEMPO_ENTRE_DANOS, function()
		emCooldown[player] = nil
	end)
end)

checkpoint1.Touched:Connect(function(outraParte)
	local player, humanoid = encontrarPlayerEHumanoid(outraParte)
	if not player or not humanoid or humanoid.Health <= 0 then
		return
	end

	checkpointsPorPlayer[player] = checkpoint1
	player:SetAttribute("CheckpointAtual", "Checkpoint 1")
end)

Players.PlayerRemoving:Connect(function(player)
	checkpointsPorPlayer[player] = nil
	emCooldown[player] = nil
	ultimoCharacterRestaurado[player] = nil
end)

for _, player in Players:GetPlayers() do
	prepararPlayer(player)
end
Players.PlayerAdded:Connect(prepararPlayer)

A Part que tocou não é aceita como identidade. O servidor sobe até um Model, exige um Player correspondente, exige Humanoid vivo e mantém cooldown separado por Player. O checkpoint guardado é uma Instance escolhida pelo servidor; o cliente não informa coordenadas.

  1. Use Play, toque o obstáculo e confira a queda de 20 pontos, no máximo uma vez por segundo.
  2. Passe no checkpoint, use Reset Character e confirme o retorno três studs acima dele.
  3. Antes de tocar o checkpoint, o respawn deve voltar ao início. No Explorer de teste, selecione Player e confira o atributo CheckpointAtual.
Seguro para esta etapa

Dano e destino são decisões do servidor. O checkpoint ainda não sobrevive ao fechamento do servidor; DataStore será ensinado no Módulo 7. Não chame isso de progresso salvo.

Exercícios e fechamento

Fácil

Imprima Health antes e depois de TakeDamage() e explique os dois valores.

Intermediário

Crie Checkpoint2 e atualize nome e destino sem aceitar Parts fora de Interacoes.

Desafiador

Teste com dois clientes e demonstre que o cooldown de um Player não bloqueia o outro.

Projeto 3 concluído: o obstáculo valida Character/Humanoid e limita dano por jogador. Projeto 5 iniciado: o percurso já restaura checkpoint durante a sessão.

  • Player e Character têm ciclos diferentes.
  • Uma peça tocada não prova identidade.
  • O servidor decide dano e checkpoint.
  • Estado por Player é limpo em PlayerRemoving.
Gabarito comentado

Fácil: guarde local antes = humanoid.Health, aplique dano e imprima antes e humanoid.Health. ForceField ou morte podem afetar o observado; registre o contexto.

Intermediário: crie outra conexão com a mesma validação e atribua a Part conhecida pelo servidor. Uma função ativarCheckpoint(checkpoint, nome) evita duplicação.

Desafiador: use Test → Server & Clients com dois clientes. Como emCooldown[player] tem chaves distintas, ambos podem receber dano no próprio ritmo.

Capítulo 4.2

Script, LocalScript, ModuleScript e locais de execução

Escolha o lado pelo tipo de responsabilidade, não pelo nome do arquivo.

Objetivos, termos e modelo mental

Pré-requisitos: 4.1 e 2.8. Você vai distinguir servidor, cliente, replicação, RunContext e módulos reutilizáveis.

Servidor
Processo que coordena a sessão e é autoridade para resultados importantes.
Cliente
Cópia executada no dispositivo de cada jogador.
Replicação
Sincronização seletiva de estado entre servidor e clientes.
RunContext
Propriedade de Script que define em qual lado ele executa.
ModuleScript
Unidade reutilizável carregada com require().
Cache
Resultado guardado para os próximos require() do mesmo ambiente.
Servidordano, itens, progresso
↔
Estado replicadocópias autorizadas
↔
Clienteinput, câmera, GUI

Os três tipos

ObjetoExecuçãoLocais didáticos desta apostila
ScriptServidor ou cliente conforme RunContext e localServerScriptService para servidor; ReplicatedStorage + RunContext Client para cliente estável
LocalScriptCliente em contêineres permitidos; não possui RunContextStarterPlayerScripts, StarterGui, StarterPack/Tool
ModuleScriptQuando outro script chama require()ReplicatedStorage se ambos os lados podem ler; ServerStorage se só servidor
Compartilhar o arquivo não compartilha a memória

Um ModuleScript exigido no servidor e no cliente produz caches separados. Alterar uma tabela do módulo no cliente não altera a tabela do servidor e não é uma forma de comunicação.

Prática guiada

Compare os dois lados e um módulo compartilhado

  1. Em ReplicatedStorage, crie ModuleScript MensagemDeContexto.
  2. Em ServerScriptService, crie Script ObservadorServidor, RunContext Server.
  3. Em ReplicatedStorage, crie Script ObservadorCliente, RunContext Client.
MensagemDeContexto.luauModuleScript · game → ReplicatedStorage · carregado separadamente por cada lado
local MensagemDeContexto = {}
local vezesChamado = 0

function MensagemDeContexto.criar(lado)
	vezesChamado += 1
	return string.format("[%s] chamada local número %d", lado, vezesChamado)
end

return MensagemDeContexto
ObservadorServidor.server.luauScript · game → ServerScriptService · servidor · início
local RunService = game:GetService("RunService")
local ReplicatedStorage = game:GetService("ReplicatedStorage")
local mensagem = require(ReplicatedStorage.MensagemDeContexto)

print("Servidor?", RunService:IsServer(), "Cliente?", RunService:IsClient())
print(mensagem.criar("SERVIDOR"))
print(mensagem.criar("SERVIDOR"))
ObservadorCliente.client.luauScript · game → ReplicatedStorage · RunContext Client · início de cada cliente
local RunService = game:GetService("RunService")
local ReplicatedStorage = game:GetService("ReplicatedStorage")
local modulo = ReplicatedStorage:WaitForChild("MensagemDeContexto")
local mensagem = require(modulo)

print("Servidor?", RunService:IsServer(), "Cliente?", RunService:IsClient())
print(mensagem.criar("CLIENTE"))
print(mensagem.criar("CLIENTE"))

Cada lado imprime chamadas 1 e 2: evidência de caches separados. O cliente usa WaitForChild() porque recebe objetos replicados; o servidor conhece o objeto editado desde o início.

  1. Use Test → Server & Clients com dois clientes. No Output, habilite a coluna Source/Context se disponível.
  2. Compare o Explorer do servidor com o de cada cliente. Cada cliente executa seu observador; o servidor executa um.
  3. Mova ObservadorServidor para ServerStorage e teste: scripts ali não executam. Devolva-o a ServerScriptService.

Se não aparecer mensagem do cliente: confira RunContext Client e se o Script está em ReplicatedStorage. Se o módulo retornar nil, confirme a linha return MensagemDeContexto. Stop e corrija a hierarquia para reiniciar.

Classifique antes de programar

Servidor: conceder moeda, aplicar dano, validar compra, salvar dados. Cliente: ler teclado, mover câmera, mostrar HUD, tocar efeito local. Ambos, com estados separados: utilitários puros e configurações públicas. “O cliente não é confiável” não significa que ele é inútil: significa que sua afirmação não basta para conceder uma vantagem.

Fácil

Classifique: câmera, preço final, texto do HUD, dano e salvamento.

Intermediário

Explique por que um ModuleScript em ReplicatedStorage não deve conter uma chave secreta.

Desafiador

Classifique vinte responsabilidades de um jogo próprio e justifique cinco casos ambíguos.

Pequeno projeto: crie um documento dentro do Studio, como comentários em um Script desativado chamado MapaDeResponsabilidades, com as colunas servidor, cliente e compartilhado. Não implemente remotes ainda.

  • RunContext define o lado de um Script.
  • LocalScript depende de local permitido.
  • ModuleScript executa quando requerido e tem cache por ambiente.
  • Resultado importante não nasce da palavra do cliente.
Gabarito comentado

Fácil: câmera e HUD são cliente; preço final, dano e salvamento são servidor.

Intermediário: ReplicatedStorage é legível pelo cliente. Segredo enviado ao cliente deixa de ser segredo, mesmo se o código estiver “escondido” em módulo.

Desafiador: efeitos podem ser previstos no cliente e confirmados pelo servidor; inventário mostrado é cliente, mas sua fonte de verdade é servidor. Justificativa importa mais que rótulo isolado.

Capítulo 4.3

Tools, StarterPack, Backpack e inventário de sessão

Construa uma ferramenta visual e entenda o que é copiado em cada respawn.

Objetivos e vocabulário

Pré-requisitos: 4.1, 4.2 e 3.1. Você criará uma Tool física, Handle, luz local, estado, cooldown e limpeza.

Tool
Objeto equipável do inventário.
Handle
Única BasePart filha direta chamada Handle, usada para segurar a Tool física.
StarterPack
Modelo inicial de ferramentas copiadas ao Backpack a cada spawn.
Backpack
Inventário daquela vida; é recriado no respawn.
Cooldown
Intervalo que impede ativações rápidas repetidas.

StarterPack não é o inventário vivo: é o molde. Ao nascer, o jogador recebe cópias no Backpack. Ao equipar, a Tool muda do Backpack para o Character; ao desequipar, volta.

Esta lanterna é deliberadamente visual

A luz será alternada no cliente. Isso é adequado para um efeito pessoal sem recompensa. Uma espada, chave, compra ou item persistente exigiria decisão do servidor e comunicação validada, ensinadas no Módulo 5.

Prática guiada · início do Projeto 4

Monte uma lanterna que se limpa ao desequipar

  1. Com o teste parado, em StarterPack crie Tool Lanterna. Defina RequiresHandle = true e CanBeDropped = false.
  2. Dentro da Tool, crie Part Handle: Size 1,1,2; Anchored false; CanCollide false; Massless true. Deve existir somente um Handle.
  3. Dentro de Handle, crie PointLight Luz: Enabled false; Range 24; Brightness 2.
  4. Dentro de Lanterna, crie LocalScript ControleLanterna. Ele executa no cliente quando a cópia da Tool chega ao Backpack.
ControleLanterna.client.luauLocalScript · game → StarterPack → Lanterna · cliente
local tool = script.Parent
local handle = tool:WaitForChild("Handle")
local luz = handle:WaitForChild("Luz")

local INTERVALO = 0.25
local ligada = false
local emCooldown = false

local function aplicarEstado()
	luz.Enabled = ligada
	print("Lanterna ligada?", ligada)
end

local function aoAtivar()
	if emCooldown then
		return
	end

	emCooldown = true
	ligada = not ligada
	aplicarEstado()

	task.delay(INTERVALO, function()
		emCooldown = false
	end)
end

local function aoDesequipar()
	ligada = false
	aplicarEstado()
end

tool.Activated:Connect(aoAtivar)
tool.Unequipped:Connect(aoDesequipar)

ligada é o estado visual; emCooldown controla frequência. Activated representa click, toque ou gatilho traseiro conforme a Tool. Unequipped restaura um estado previsível.

  1. Use Play. Selecione o slot da lanterna e ative. A PointLight deve alternar e o Output do cliente deve informar o estado.
  2. Desequipe com outra tecla/slot: a luz deve apagar. Equipe novamente e confirme.
  3. Use Reset Character. O Backpack e a Tool são recriados a partir do StarterPack; a nova lanterna começa apagada.
  4. No Explorer do teste, observe a Tool sair de Backpack e entrar no Character quando equipada.

Diagnóstico: personagem preso geralmente indica Handle Anchored; ferramenta invisível no slot indica que ela não está em StarterPack; espera infinita indica nome incorreto de Handle ou Luz. Use Stop, corrija o molde em StarterPack e teste novamente.

Exercícios e incremento

Fácil

Altere Range e Brightness e registre qual combinação continua confortável.

Intermediário

Adicione uma segunda PointLight de cor diferente e alterne ambas pela mesma função.

Desafiador

Crie três estados locais — apagada, fraca e forte — avançando circularmente sem usar conceito futuro.

Projeto 4 iniciado: lanterna física, estado local, cooldown e limpeza já funcionam. No próximo capítulo, o input sai do evento genérico da Tool e entra em ações nomeadas.

  • StarterPack é molde; Backpack é inventário vivo.
  • Tool física exige um único Handle não ancorado.
  • Eventos de input da Tool são tratados no cliente.
  • Efeito importante para outros jogadores exigiria servidor.
Gabarito comentado

Fácil: não existe um único valor ideal; compare alcance, claridade e desconforto visual. Uma resposta válida registra os valores testados.

Intermediário: obtenha a segunda luz com WaitForChild e atribua Enabled = ligada dentro de aplicarEstado().

Desafiador: use local estado = 0, avance com estado = (estado + 1) % 3 e escolha Enabled/Brightness com condições. Várias soluções são válidas.

Pré-requisitos: 4.2 e 4.3. Neste primeiro contato não existe botão touch: ScreenGui e GuiButton ainda não foram ensinados.

InputContext

Bool
Tipo de ação com estados pressionado e liberado.

Movimento, câmera, menu e outros inputs possuem bindings conhecidos e alguns reservados. Escolha L e ButtonY para esta prática e verifique conflitos no seu projeto.

Prática guiada · Projeto 4 multiplataforma, parte 1

Converta a lanterna para uma ação

  1. Selecione Workspace e, em Properties, defina PlayerScriptsUseInputActionSystem = Enabled, conforme a recomendação atual.
  2. Em ReplicatedStorage crie Folder Inputs. Dentro, crie InputContext Jogabilidade, Enabled true.
  3. Dentro do contexto, crie InputAction AlternarLanterna, Type Bool.
  4. Dentro da ação, crie dois InputBindings: Teclado com KeyCode L e Gamepad com KeyCode ButtonY.
  5. Apague StarterPack → Lanterna → ControleLanterna para que a mesma intenção não seja processada duas vezes.
  6. Dentro de AlternarLanterna, crie Script AoAlternarLanterna, RunContext Client.
AoAlternarLanterna.client.luauScript · ReplicatedStorage → Inputs → Jogabilidade → AlternarLanterna · cliente
local Players = game:GetService("Players")
local player = Players.LocalPlayer
local inputAction = script.Parent

local ligada = false

local function encontrarLanternaEquipada()
	local character = player.Character
	if not character then
		return nil
	end
	return character:FindFirstChild("Lanterna")
end

local function aoPressionar()
	local lanterna = encontrarLanternaEquipada()
	if not lanterna or not lanterna:IsA("Tool") then
		warn("Equipe a Lanterna antes de usar a ação.")
		return
	end

	local handle = lanterna:FindFirstChild("Handle")
	local luz = handle and handle:FindFirstChild("Luz")
	if not luz or not luz:IsA("PointLight") then
		warn("A Lanterna equipada não possui Handle/Luz válidos.")
		return
	end

	ligada = not ligada
	luz.Enabled = ligada
	print("AlternarLanterna recebeu input. Ligada?", ligada)
end

inputAction.Pressed:Connect(aoPressionar)

player.CharacterRemoving:Connect(function()
	ligada = false
end)

O Script escuta a ação, não a tecla. A guard clause exige a Tool equipada e valida sua estrutura. O estado é local e reinicia quando o Character é removido.

  1. Use Play, equipe a lanterna e pressione L. Ela deve alternar uma vez por pressão.
  2. Abra Test → Controller Emulator, escolha um gamepad e pressione ButtonY. O mesmo callback deve executar.
  3. Pressione L sem equipar. Espere warning, não erro. Use Stop para recomeçar.

Se a ação não dispara: confira Workspace.PlayerScriptsUseInputActionSystem, hierarquia InputContext → InputAction → InputBinding, Type Bool, Enabled e RunContext Client. Se dispara duas vezes, procure o LocalScript antigo da Tool ou bindings duplicados.

Pressed, Released e StateChanged

Para uma ação Bool, Pressed ocorre na transição false → true e Released na volta. StateChanged serve para observar ambos. Gatilhos analógicos usam limiares de pressão e liberação; para um simples alternador, Pressed é suficiente e evita alternar também ao soltar.

Fácil

Troque a tecla L por F e comprove que o código não mudou.

Intermediário

Conecte Released apenas para imprimir “soltou”, sem alterar a luz.

Desafiador

Crie outro contexto desativado e explique, com teste, por que sua ação não dispara até Enabled virar true.

Incremento do Projeto 4: teclado e gamepad agora convergem para a mesma intenção. Touch permanece pendente de propósito até 4.6.

  • Ação descreve intenção; binding descreve hardware.
  • Uma ação Bool oferece Pressed e Released.
  • O código não precisa conhecer cada tecla.
  • Nenhuma GUI foi usada antes de ser ensinada.
Gabarito comentado

Fácil: altere apenas KeyCode do binding Teclado. A função continua conectada à ação.

Intermediário: use inputAction.Released:Connect(function() print("soltou") end). Não inverta ligada nessa conexão.

Desafiador: um InputContext desabilitado também desabilita suas ações. Depois do teste, volte ao contexto Jogabilidade para não criar conflito.

Objetivos e vocabulário

Pré-requisitos: 4.4 e 4.5. Agora ScreenGui e GuiButton já são conhecidos, então podemos criar o binding touch sem antecipar conceitos.

Adaptação não é apenas encolher

Um telefone vertical, um tablet e uma TV mudam espaço, distância de leitura e input. Prática guiada · Projetos 4 e 5 concluídos

Adicione touch e adapte o HUD

  1. Em StarterGui → HUDPercurso, confirme ScreenInsets CoreUISafeInsets e ClipToDeviceSafeArea true.
  2. Dentro de Painel, crie UISizeConstraint LimitesPainel: MinSize 280,150 e MaxSize 720,220. Mantenha largura do Painel em Scale.
  3. Nos TextLabels, use TextWrapped true. Evite TextScaled em parágrafos; escolha TextSize legível e teste.
  4. Dentro de HUDPercurso, crie TextButton BotaoLanterna: Text “Lanterna”; AnchorPoint 1,1; Position {1,-24},{1,-120}; Size {0,120},{0,56}; Active/Selectable true. Ele fica fora de Painel para ter zona própria.
  5. Selecione ReplicatedStorage → Inputs → Jogabilidade → AlternarLanterna e crie terceiro InputBinding Touch. Na propriedade UIButton, selecione StarterGui → HUDPercurso → BotaoLanterna.
  6. Não adicione outro LocalScript ao botão. O binding encaminha sua pressão para a mesma InputAction de 4.4.

  4. Com gamepad, alcance BotaoMensagem e BotaoLanterna pelo foco. Confirme contorno visível e Activated no botão de mensagem.
  5. Troque textos por versões propositalmente longas, como “Ponto de verificação intermediário alcançado”, e confirme quebra sem sobreposição.

Prepare a localização sem fingir tradução

Mantenha textos visíveis em objetos de texto com AutoLocalize habilitado quando usar captura automática. Publicação, idiomas e revisão da tabela de localização pertencem a um módulo posterior. Tradução automática não dispensa revisão humana: nomes próprios, contexto e comprimento precisam ser verificados.

Teste de acessibilidade

Afaste-se da tela, reduza o brilho, use cenário claro e escuro, tente apenas gamepad e depois apenas touch. Cor não deve ser a única forma de comunicar estado; combine texto, forma ou ícone. Mantivemos TextScaled = false para não impedir a preferência de tamanho de texto do jogador; se você animar a GUI no futuro, consulte GuiService.ReducedMotionEnabled e ofereça uma alternativa sem deslocamento.

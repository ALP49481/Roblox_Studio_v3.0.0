Capítulo 9.1

Threat modeling, texto, políticas e moderação

Pense como um defensor: o que pode ser controlado, abusado ou exibido indevidamente?

Objetivos, pré-requisitos e vocabulário

Pré-requisitos: 5.1–5.5, 7.4 e 8.5. Você criará um modelo de ameaças, filtrará texto fora do chat, adotará falha segura e distinguirá prevenção, detecção e resposta.

Threat model
Mapa do que protegemos, de quem, por quais caminhos e com qual impacto.
UGC
Conteúdo criado ou fornecido pelo usuário, como texto, desenho ou áudio.
Falha segura
Quando uma dependência falha, o sistema escolhe o estado menos arriscado.
Política
Regra da plataforma ou condição de elegibilidade que o sistema deve respeitar.
Moderação
Processo de prevenir, revisar e responder a conteúdo ou comportamento impróprio.

Do ativo valioso ao teste hostil

O explorador determinado controla seu cliente: memória local, scripts replicados, chamadas de remotes e parte da simulação física. Ele pode trocar parâmetros, repetir uma ação mil vezes, omitir campos e combinar estados improváveis. Portanto, modele cada fluxo em cinco perguntas: o que vale proteger, quem decide, qual entrada cruza a fronteira, qual pior caso e qual evidência denuncia abuso?

Não grave texto bruto, tokens, chaves, mensagens privadas ou perfil completo. Prefira códigos de motivo e contagens. Logs devem ajudar a investigar sem criar outro vazamento.

Prática guiada — placa com texto filtrado

Projeto aberto: cópia de SimuladorEnxuto chamada AuditoriaProducao. Objetivo: enviar texto no cliente, validar e filtrar no servidor, e nunca exibir o original se a API falhar.

  1. Em ReplicatedStorage, crie Folder SafetyRemotes e dentro um RemoteEvent chamado SubmitSignText.
  2. Em Workspace, crie Model SafetyLab, Part Sign, SurfaceGui na face frontal e TextLabel chamado Message. Defina o texto inicial como “Aguardando mensagem”.
  3. Em StarterGui, crie ScreenGui SafetyGui; dentro, TextBox Input, TextButton Submit e TextLabel Status. Ajuste tamanho/posição usando o que aprendeu no Módulo 4.
  4. Dentro de SafetyGui, crie LocalScript SubmitSignText. Em ServerScriptService, crie Script de mesmo nome.
SubmitSignText.client.luauLocalScript · StarterGui/SafetyGui · cliente · após carregar a interface
--!strict
local ReplicatedStorage = game:GetService("ReplicatedStorage")

local gui = script.Parent :: ScreenGui
local input = gui:WaitForChild("Input") :: TextBox
local submit = gui:WaitForChild("Submit") :: TextButton
local status = gui:WaitForChild("Status") :: TextLabel
local remote = ReplicatedStorage:WaitForChild("SafetyRemotes"):WaitForChild("SubmitSignText") :: RemoteEvent

submit.Activated:Connect(function()
	status.Text = "Enviando para revisão…"
	remote:FireServer(input.Text) -- pedido, não decisão
end)

remote.OnClientEvent:Connect(function(ok: boolean, message: string)
	status.Text = message
	if ok then input.Text = "" end
end)
SubmitSignText.server.luauScript · ServerScriptService · servidor · inicia com a sessão
--!strict
local ReplicatedStorage = game:GetService("ReplicatedStorage")
local TextService = game:GetService("TextService")

local remote = ReplicatedStorage:WaitForChild("SafetyRemotes"):WaitForChild("SubmitSignText") :: RemoteEvent
local label = workspace:WaitForChild("SafetyLab"):WaitForChild("Sign"):WaitForChild("SurfaceGui"):WaitForChild("Message") :: TextLabel
local lastRequest: {[Player]: number} = {}
local COOLDOWN = 3
local MAX_BYTES = 200

remote.OnServerEvent:Connect(function(player: Player, raw: unknown)
	if typeof(raw) ~= "string" or #raw == 0 or #raw > MAX_BYTES then
		remote:FireClient(player, false, "Use entre 1 e 200 bytes.")
		return
	end
	local now = os.clock()
	if now - (lastRequest[player] or 0) < COOLDOWN then
		remote:FireClient(player, false, "Espere alguns segundos.")
		return
	end
	lastRequest[player] = now

	local success, filtered = pcall(function()
		local result = TextService:FilterStringAsync(raw, player.UserId)
		return result:GetNonChatStringForBroadcastAsync()
	end)
	if not success then
		warn("[Safety] filtro indisponível; texto bruto descartado")
		label.Text = "Mensagem indisponível"
		remote:FireClient(player, false, "Não foi possível revisar o texto. Tente depois.")
		return
	end

	label.Text = filtered
	remote:FireClient(player, true, "Mensagem publicada com filtro.")
end)

Teste: use Test → Start com dois clientes. Envie texto e confira que ambos veem a versão filtrada. Troque temporariamente a função dentro do pcall por error("falha simulada"): deve aparecer apenas “Mensagem indisponível”, nunca o texto original. Restaure a função antes de salvar. Para reiniciar, Stop; para desfazer, apague apenas os objetos SafetyLab, SafetyGui, SafetyRemotes e os dois scripts.

Diagnóstico: Infinite yield indica nome/caminho incorreto; nenhum clique indica LocalScript fora de StarterGui; texto bruto após falha significa violação crítica. Filtre depois do envio, não a cada tecla.

Chat, PolicyService e resposta proporcional

TextChatService oferece filtragem e moderação para o chat moderno, mas você continua responsável por todo texto fora dele. Antes de recursos dependentes de região, idade ou plataforma, consulte PolicyService:GetPolicyInfoForPlayerAsync() no servidor, dentro de pcall; se falhar, use o estado restritivo. Para reincidência, documente evidência e use o sistema de bans do Creator Dashboard/Ban API; Player:Kick() encerra apenas a sessão atual.

Conteúdo público também exige questionário de Maturidade e Conformidade correto e atualizado. Moderar não é “punir todo erro”: rejeite pedidos inválidos, limite frequência, registre sinais agregados e escale somente quando houver evidência.

Exercícios e incremento

Fácil

Acrescente ao threat model quem é o dono da verdade em cada um dos quatro fluxos.

Intermediário

Adapte a placa para texto por jogador com GetNonChatStringForUserAsync e explique por que o resultado pode variar.

Desafiador

Monte cinco testes hostis para loja e combate, incluindo NaN, spam e estado impossível, sem executar exploit externo.

Incremento do Projeto 9 e 10: crie uma matriz de ameaças e políticas para simulador e arena, com ativo, limite de confiança, prevenção, detecção, resposta e responsável.

  • Sei listar capacidades do cliente hostil.
  • Filtro todo texto exibido a outros usuários.
  • Falha do filtro nunca libera texto bruto.
  • Uso políticas e maturidade como requisitos de produto.
  • Logs não contêm segredos ou conteúdo sensível.
Gabarito comentado

Fácil: moedas, itens, dano e progresso pertencem ao servidor; o cliente é dono apenas de intenção e feedback local. Texto passa pelo servidor e serviço de filtragem.

Intermediário: gere o TextFilterResult uma vez e obtenha a representação destinada a cada usuário. Não reutilize texto bruto como fallback.

Desafiador: uma boa bateria inclui tipo errado, infinito/NaN, quantidade extrema, pedido fora de alcance e rajada. O esperado é rejeição sem mutação nem erro não tratado. Há outras soluções válidas.

Capítulo 9.2

Performance, memória, rede e profiling

Otimize a causa medida, no dispositivo relevante, e preserve uma comparação reproduzível.

Objetivos e vocabulário

Pré-requisitos: 6.3, 8.1 e projetos integrados. Você estabelecerá baseline, reproduzirá custo controlado, localizará um escopo no MicroProfiler e comprovará a correção.

Baseline
Medição inicial, feita sob condições registradas.
Budget
Limite planejado de tempo, memória ou tráfego.
Profiler
Ferramenta que mostra onde recursos são gastos.
Leak
Memória ou conexão que permanece sem necessidade.
Regressão
Problema que reaparece após uma mudança.

Medir antes de mexer

Performance tem pelo menos quatro lados: CPU, GPU, memória e rede; carregamento é outro resultado importante. Um PC rápido pode esconder o custo que derruba um celular. Registre dispositivo/emulação, número de jogadores, qualidade gráfica, cenário e duração. Depois compare a mesma cena.

SintomaFerramenta inicialPróxima pergunta

memória cresce continuamenteDeveloper Console → Memoryinstâncias, conexões ou assets?
servidor lento/ping altoServer Jobs/Statsheartbeat abaixo do esperado?
script caroScript Performance/Profilerqual função e frequência?
rede altaDeveloper Console → Networkestado repetido ou árvore grande?

Prática guiada — gargalo controlado e correção

Projeto aberto: AuditoriaProducao. Em ServerScriptService, crie Script PerformanceLab. O modo inicial é seguro; o modo ruim existe só para um teste curto no Studio.

PerformanceLab.server.luauScript · ServerScriptService · servidor · inicia com a sessão
--!strict
local RunService = game:GetService("RunService")

local MODE = "FIXED" -- altere temporariamente para "BAD"
local SAMPLE_COUNT = 250
local accumulator = 0

local function measuredWork()
	debug.profilebegin("PerformanceLabWork")
	local total = 0
	for index = 1, SAMPLE_COUNT do
		total += math.sqrt(index)
	end
	debug.profileend()
	return total
end

local connection: RBXScriptConnection
connection = RunService.Heartbeat:Connect(function(deltaTime: number)
	if MODE == "BAD" then
		-- Intencionalmente ruim: trabalho desnecessário em todo frame.
		measuredWork()
		return
	end

	-- Versão corrigida: o relatório só precisa de 5 atualizações por segundo.
	accumulator += deltaTime
	if accumulator < 0.2 then return end
	accumulator %= 0.2
	measuredWork()
end)

script.Destroying:Connect(function()
	connection:Disconnect()
end)
  1. Use Play e espere 30 segundos com MODE = "FIXED". Abra View → Performance e Developer Console (F9); registre FPS, memória e atividade do script.
  2. Abra o MicroProfiler com Ctrl+Alt+F6, pause com Ctrl+P e procure PerformanceLabWork.
  3. Stop, mude para MODE = "BAD", repita a mesma cena por 30 segundos e compare frequência/tempo do escopo.
  4. Volte obrigatoriamente para FIXED, rode de novo e salve a tabela antes/depois. Nunca publique a versão ruim.

Resultado: o marcador ocorre aproximadamente cinco vezes por segundo no modo corrigido e uma vez por frame no ruim. O tamanho do custo depende do dispositivo; a evidência principal é frequência e tempo, não uma promessa de FPS.

Erros: marcador ausente indica nome alterado ou script não executado; resultado igual pode significar trabalho pequeno demais para o dispositivo — aumente apenas SAMPLE_COUNT com cuidado e reverta; memória crescente não é causada por este cálculo puro, então procure instâncias ou conexões. Para desfazer, apague PerformanceLab.

Correções que preservam o design

Prefira evento a polling; reduza frequência; envie mudança em vez de estado repetido; produza efeitos visuais no cliente quando o servidor só precisa validar o resultado; destrua instâncias e desconecte conexões; use pooling apenas quando a medição mostrar que criar/destruir repetidamente é caro. Pooling tem custo de memória e complexidade, portanto não é “sempre mais rápido”.

Regression test

Guarde cenário, números, captura do perfil e limite aceitável. Depois de cada atualização grande, repita o mesmo teste no dispositivo mais fraco que você pretende suportar.

Exercícios e relatório principal

Fácil

Troque o intervalo corrigido para 0,5 s e calcule quantas chamadas espera em 30 s.

Intermediário

Encontre uma conexão que possa sobreviver ao objeto e implemente desligamento explícito.

Desafiador

Faça um teste com dois e seis clientes e compare servidor, cliente e rede sem mudar a cena.

Projeto principal: entregue um relatório do simulador ou arena com hipótese, ambiente, baseline, perfil, uma mudança, resultado, trade-off e limite de regressão.

  • Separo CPU, GPU, memória, rede e carregamento.
  • Registro condições do teste.
  • Uso profiler para localizar causa.
  • Comparo antes/depois na mesma cena.
  • Não publico o gargalo didático.
Gabarito comentado

Fácil: 30 ÷ 0,5 = cerca de 60 chamadas; pequenas diferenças decorrem do início/fim do teste.

Intermediário: guarde o RBXScriptConnection e chame Disconnect() ao destruir/desativar o dono. Evite criar outra conexão a cada respawn sem limpar a anterior.

Desafiador: mantenha duração, posição e ações equivalentes. A conclusão deve apontar a métrica que mudou e não confundir correlação com causa.

Capítulo 9.3

Assets, avatares, propriedade, permissões e propriedade intelectual

Um ID que funciona hoje não basta: você precisa saber de quem é, onde pode ser usado e como substituí-lo.

Objetivos e vocabulário

Pré-requisitos: 1.4, 4.1, 6.4 e 8.3. Você fará inventário de assets, verificará permissões/moderação, distinguirá R6 de R15 e criará um plano de migração de proprietário.

Asset ID
Identificador de um recurso armazenado na nuvem Roblox.
Owner
Conta ou grupo que detém o asset.
Licença
Permissão legal de uso, que não nasce só porque o arquivo está acessível.
Package
Conjunto reutilizável de instâncias com versões e permissões.
Rig
Estrutura de partes/juntas que permite mover um personagem.

O inventário de dependências visuais

Imagens, meshes, áudio, animações e packages são assets na nuvem. Privacidade determina quem pode usar; moderação determina se pode aparecer; propriedade determina quem consegue manter. Um asset privado da conta pessoal pode quebrar quando a experiência pertence ao grupo. Conteúdo da Toolbox também exige revisão de scripts, licença e procedência.

Prática guiada — manifesto auditável

Projeto aberto: AuditoriaProducao. Em ReplicatedStorage, crie Folder Shared se não existir e dentro um ModuleScript AssetManifest. Em ServerScriptService, crie Script AuditAssets. Substitua os IDs de exemplo pelos seus antes de considerar a auditoria aprovada.

AssetManifest.luauModuleScript · ReplicatedStorage/Shared · carregado por quem chamar require
--!strict
export type AssetRecord = {
	name: string,
	id: number,
	kind: string,
	expectedOwner: string,
	licenseEvidence: string,
	status: string,
}

local assets: {AssetRecord} = {
	{name = "ArenaMusic", id = 0, kind = "Audio", expectedOwner = "SEU_GRUPO", licenseEvidence = "Creator Dashboard", status = "REPLACE_ID"},
	{name = "AttackAnimation", id = 0, kind = "Animation", expectedOwner = "SEU_GRUPO", licenseEvidence = "arquivo-fonte", status = "REPLACE_ID"},

return table.freeze(assets)
AuditAssets.server.luauScript · ServerScriptService · servidor · inicia com a sessão de teste
--!strict
local ReplicatedStorage = game:GetService("ReplicatedStorage")
local assets = require(ReplicatedStorage:WaitForChild("Shared"):WaitForChild("AssetManifest"))

local seen: {[number]: string} = {}
local failures = 0
for _, asset in assets do
	if asset.id <= 0 or asset.status ~= "APPROVED" then
		failures += 1
		warn("[AssetAudit] pendente:", asset.name, asset.status)
	end
	if asset.licenseEvidence == "" or asset.expectedOwner == "" then
		failures += 1
		warn("[AssetAudit] falta evidência:", asset.name)
	end
	if seen[asset.id] then
		warn("[AssetAudit] ID repetido:", asset.name, "e", seen[asset.id])
	else
		seen[asset.id] = asset.name
	end
end

print(string.format("[AssetAudit] %d assets; %d pendências", #assets, failures))
  1. Abra View → Asset Manager e Creator Dashboard. Para cada ID, confira owner, permissão, moderação e local de uso; o script não descobre licença sozinho.
  2. Pesquise no Explorer por rbxassetid://, AnimationId, SoundId, Texture, MeshId e referências de package. Adicione ao manifesto.
  3. Marque APPROVED apenas com evidência. Use Play e exija “0 pendências”.
  4. Para reiniciar, Stop e corrija o manifesto. Para desfazer, remova somente os dois scripts.

Diagnóstico: asset invisível pode estar moderando, sem permissão, arquivado ou com ID/tipo errado. Não “conserte” copiando material sem licença.

R6, R15, customização e migração

R6 é o rig legado com seis partes; R15 possui quinze partes e suporte mais amplo a movimento/acessórios em camadas. Não suponha nomes de membros sem testar o modo configurado. Para trocar owner, publique os assets no grupo, conceda permissões, substitua IDs numa branch/cópia privada, teste animação/áudio/mesh, publique gradualmente e mantenha o mapa antigo→novo para rollback. Packages ajudam consistência, mas auto-update deve ser consciente: uma atualização não testada pode afetar todas as cópias.

Exercícios e auditoria principal

Fácil

Adicione três assets reais e suas localizações no Explorer.

Intermediário

Teste a arena em R6 e R15 e registre qualquer suposição quebrada.

Desafiador

Escreva uma migração de conta pessoal para grupo com validação e rollback.

Projeto principal: inventário completo de IDs, owner, licença, privacidade, moderação e substituto do simulador/arena.

  • Sei localizar e documentar cada asset.
  • Acesso não equivale a licença.
  • Owner combina com a experiência.
  • Testo o rig realmente suportado.
  • Migração preserva mapa antigo→novo.
Gabarito comentado

Fácil: um registro válido contém ID positivo, tipo correto, caminho, owner confirmado e evidência.

Intermediário: procure nomes rígidos como Torso, proporções, acessórios e animações. Prefira abstrações como HumanoidRootPart e teste ambos quando ambos forem anunciados.

Desafiador: publicar cópias no grupo, registrar novos IDs, trocar numa versão privada, testar, liberar, observar e manter reversão. Não arquive o original antes da estabilidade.

Capítulo 9.4

Publicação, configuração, lançamento e rollback

Publicar uma versão privada é o começo de uma liberação controlada, não um salto direto ao público.

Objetivos e vocabulário

Pré-requisitos: 6.3–6.4, 7.3 e 9.1–9.3. Você publicará um teste privado, fará checklist de release e planejará rollback compatível com o schema de dados.

Staging
Ambiente/experiência separada para validar uma versão antes do público.
Rollout
Liberação gradual para limitar impacto.
Rollback
Retorno planejado a uma versão segura.
Metadata
Nome, descrição, ícone, miniaturas e informações de descoberta.
Schema
Formato persistido dos dados do jogador.

Três coisas diferentes

Salvar localmente cria arquivo no computador. Publicar no Roblox envia uma versão do place à nuvem. Tornar público altera quem pode entrar. Novas experiências começam privadas; preserve isso durante os testes.

Prática guiada — release privada reproduzível

Projeto aberto: AuditoriaProducao com zero pendências críticas conhecidas. Use uma experiência de teste, não a experiência pública.

  1. Stop qualquer playtest. Use File → Save to File e crie uma cópia datada.
  2. Use File → Publish to Roblox As…, escolha/crie a experiência de staging sob o owner correto. Confirme nome, descrição honesta, creator e dispositivos realmente testados. Mantenha-a privada.
  3. No Creator Dashboard, abra a experiência → Configure. Revise Places, Permissions, Devices, Maturity & Compliance e acesso de colaboradores pelo menor privilégio.
  4. Adicione ícone quadrado de pelo menos 512×512 e miniatura 16:9 idealmente 1920×1080, ambos representando gameplay real e aguardando moderação.
  5. Em Studio, execute teste de servidor com dois clientes; no app Roblox, faça smoke test do link privado com uma conta autorizada.
  6. Registre número/horário da versão, checksum/tag do código, schema de dados, responsável e resultado. Abra Version History e confirme onde reverteria, sem efetuar rollback desnecessário.
ReleaseGuard.server.luauScript · ServerScriptService · servidor · verifica contrato ao iniciar
--!strict
local ReplicatedStorage = game:GetService("ReplicatedStorage")

local RELEASE_ID = "staging-2026-08-26-01"
local DATA_SCHEMA_VERSION = 3
local requiredPaths = {
	{"Remotes"},
	{"Shared", "AssetManifest"},
}

local failures = 0
for _, pathParts in requiredPaths do
	local current: Instance? = ReplicatedStorage
	for _, name in pathParts do
		current = current and current:FindFirstChild(name)
	end
	if not current then
		failures += 1
		warn("[ReleaseGuard] ausente:", table.concat(pathParts, "/"))
	end
end

if failures > 0 then
	error(string.format("Release %s bloqueada no teste: %d requisito(s) ausente(s)", RELEASE_ID, failures))
end
print("[ReleaseGuard] aprovado", RELEASE_ID, "schema", DATA_SCHEMA_VERSION)

Resultado: a experiência continua privada, acessível só a autorizados; Output mostra “aprovado”; a ficha de release aponta versão e rollback. Se o guard falhar, corrija o caminho ou o requisito — não remova a verificação para “ficar verde”. Para reiniciar, Stop/Play; para desfazer, remova o script apenas após incorporar a verificação à suíte real.

Rollback que não apaga progresso

Version History pode restaurar o place, mas não volta automaticamente os DataStores. Uma versão antiga pode não compreender dados novos. Migrações devem ser compatíveis: adicione campos com padrão, preserve campos desconhecidos quando possível e só remova depois de janela segura. Se o schema novo é incompatível, o rollback precisa incluir código capaz de ler ambos ou uma correção à frente.

Servidor antigo continua vivo

Publicar não troca instantaneamente todos os servidores existentes. Planeje coexistência de versões, contratos de remote e dados compatíveis; reiniciar servidores é uma decisão operacional com impacto nos jogadores.

Exercícios e release principal

Fácil

Escreva cinco itens de smoke test para a primeira sessão.

Intermediário

Crie um campo novo opcional no perfil e prove que a versão anterior não destrói os demais campos.

Desafiador

Simule uma versão ruim em staging, execute rollback e documente a decisão sem tocar na produção.

Projeto principal: pacote de release privada com checklist de segurança, performance, assets, dados, dispositivos, metadata, responsáveis, observação e rollback.

  • Distingo salvar, publicar e tornar público.
  • Staging usa owner e configurações corretos.
  • Metadata descreve gameplay real.
  • Rollback considera place e dados.
  • Versões coexistentes mantêm contratos compatíveis.
Gabarito comentado

Fácil: entrar, carregar perfil, completar ciclo principal, desconectar/reentrar e testar fluxo crítico em outro dispositivo são um núcleo válido.

Intermediário: leitura usa padrão quando o campo falta; gravação copia/preserva campos que não conhece. Teste fixture antigo e novo.

Desafiador: registre sintoma, limiar, versão alvo, ação, verificação posterior e responsável. Rollback é ensaiado antes da emergência.

Prática guiada — concessão persistente exatamente uma vez

Projeto aberto: uma cópia privada publicada de AuditoriaProducao, com Studio Access to API Services habilitado apenas para teste consciente. Crie um Developer Product barato de teste no Creator Dashboard e copie seu ID. Em ServerScriptService, crie Script ReceiptService. Esta prática usa DataStore isolado; em projeto real, integre recibo e moeda à mesma fila/perfil do Módulo 7.

ReceiptService.server.luauScript · ServerScriptService · servidor · um único registrador de recibos
--!strict
local DataStoreService = game:GetService("DataStoreService")
local MarketplaceService = game:GetService("MarketplaceService")
local Players = game:GetService("Players")

local PRODUCT_ID = 123456789 -- substitua pelo ID do seu produto
local COINS_GRANTED = 100
local store = DataStoreService:GetDataStore("PurchaseLabV1")

local function grantOnce(player: Player, purchaseId: string): boolean
	local success, profile = pcall(function()
		return store:UpdateAsync("player_" .. player.UserId, function(old)
			local data = old or {coins = 0, processedReceipts = {}}
			data.processedReceipts = data.processedReceipts or {}
			if data.processedReceipts[purchaseId] then
				return data -- repetição: já concedido, sem somar
			end
			data.coins = math.max(0, tonumber(data.coins) or 0) + COINS_GRANTED
			data.processedReceipts[purchaseId] = true
			return data
		end)
	end)
	if not success or typeof(profile) ~= "table" then
		warn("[Receipt] gravação inconclusiva; aguardando nova entrega")
		return false
	end
	player:SetAttribute("PurchaseLabCoins", profile.coins)
	return profile.processedReceipts[purchaseId] == true
end

local function handleReceipt(receiptInfo)
	if receiptInfo.ProductId ~= PRODUCT_ID then
		warn("[Receipt] produto sem handler:", receiptInfo.ProductId)
		return Enum.ReceiptDecision.NotProcessedYet
	end
	local player = Players:GetPlayerByUserId(receiptInfo.PlayerId)
	if not player then
		return Enum.ReceiptDecision.NotProcessedYet
	end
	local granted = grantOnce(player, tostring(receiptInfo.PurchaseId))
	return if granted then Enum.ReceiptDecision.Processed else Enum.ReceiptDecision.NotProcessedYet
end

MarketplaceService:BindReceiptHandler(
	Enum.ReceiptType.DeveloperProduct,
	handleReceipt,
	{PRODUCT_ID}
)

Leitura: moeda e marcador do PurchaseId são alterados no mesmo UpdateAsync. Se a resposta se perde depois de gravar, o Roblox pode reenviar; o marcador impede soma dupla. Jogador ausente, produto desconhecido ou falha retorna NotProcessedYet. Só retorne Processed após confirmação persistente.

  1. Substitua o ID. Use o fluxo oficial de teste; compras de teste podem custar Robux real, então mantenha preço baixo e confirme antes.
  2. Observe PurchaseLabCoins em Player → Attributes. Registre o PurchaseId apenas em ambiente de teste sem expor dados desnecessários.
  3. Para provar idempotência sem nova cobrança, extraia grantOnce para ModuleScript e crie teste que chama duas vezes com o mesmo ID fictício em um DataStore de teste; saldo deve subir uma vez.
  4. Simule falha antes do UpdateAsync; espere NotProcessedYet. Restaure antes de publicar.

Diagnóstico: concessão no evento PromptProductPurchaseFinished é insegura; duas concessões indicam marcador fora da mesma atualização; recibo preso indica produto sem handler, jogador ausente ou falha — investigue, não force Processed. Para desfazer, remova o produto de teste da interface e o script; não reutilize o DataStore de laboratório em produção.

Informação de produto e preço personalizado

Para mostrar nome e preço, um LocalScript de loja chama MarketplaceService:GetProductInfoAsync(PRODUCT_ID, Enum.InfoType.Product) dentro de pcall. Isso importa quando preços gerenciados/personalizados podem variar por usuário. Falha da API oculta/desabilita a compra; não invente preço nem confie em preço vindo do cliente para conceder algo.

ProductCard.client.luauLocalScript · StarterGui/ShopGui/ProductCard · cliente · carrega a apresentação, não concede
--!strict
local MarketplaceService = game:GetService("MarketplaceService")
local PRODUCT_ID = 123456789
local card = script.Parent
local success, info = pcall(function()
	return MarketplaceService:GetProductInfoAsync(PRODUCT_ID, Enum.InfoType.Product)
end)
if success then
	card.Text = string.format("%s · %s Robux", info.Name, tostring(info.PriceInRobux))
	card.Active = true
else
	card.Text = "Produto indisponível"
	card.Active = false
end

Capítulo 9.6

Analytics, experimentos, LiveOps e manutenção

Comece por uma pergunta; registre o evento depois do fato; mude com hipótese e guardrail.

Objetivos e vocabulário

Pré-requisitos: 7.4, 9.2, 9.4 e 9.5. Você desenhará funil de onboarding, registrará economia após sucesso, formulará experimento com proteção e criará rotina de manutenção.

KPI
Métrica-chave ligada a um objetivo.
Funil
Sequência de etapas usada para localizar abandono.
Hipótese
Previsão testável de causa e efeito.
Guardrail
Métrica-limite que impede ganho aparente às custas de dano.
LiveOps
Operação contínua após o lançamento: conteúdo, correções e acompanhamento.

Pergunta → evento → decisão

“Colete tudo” produz ruído e risco. Pergunte: em qual etapa iniciantes abandonam a primeira missão? Então registre poucas etapas estáveis. Economia registra depois da fonte ou gasto confirmado; evento customizado registra comportamento específico. Gráficos podem levar cerca de 24 horas, mas View Events oferece inspeção quase em tempo real.

PerguntaEventoDecisão possível

Analytics não substitui segurança

O servidor registra fatos autoritativos. Não envie texto livre, segredo ou identificador desnecessário; respeite limites e use nomes de evento com cardinalidade controlada.

Prática guiada — funil mínimo no servidor

Projeto aberto: staging privado de AuditoriaProducao. Em ServerScriptService, crie ModuleScript ProductionAnalytics. Os sistemas autoritativos chamam as funções somente depois de cada marco confirmado.

ProductionAnalytics.luauModuleScript · ServerScriptService · servidor · chamado após fatos confirmados
--!strict
local AnalyticsService = game:GetService("AnalyticsService")

local ProductionAnalytics = {}
local loggedSteps: {[Player]: {[number]: boolean}} = {}

function ProductionAnalytics.logOnboardingStep(player: Player, step: number, stepName: string)
	loggedSteps[player] = loggedSteps[player] or {}
	if loggedSteps[player][step] then return end
	loggedSteps[player][step] = true
	local success, message = pcall(function()
		AnalyticsService:LogOnboardingFunnelStepEvent(player, step, stepName)
	end)
	if not success then warn("[Analytics] onboarding falhou:", message) end
end

function ProductionAnalytics.logCoinSource(player: Player, amount: number, endingBalance: number, sku: string)
	assert(amount > 0 and math.isfinite(amount), "amount inválido")
	assert(endingBalance >= 0 and math.isfinite(endingBalance), "saldo inválido")
	local success, message = pcall(function()
		AnalyticsService:LogEconomyEvent(
			player,
			Enum.AnalyticsEconomyFlowType.Source,
			"Coins",
			amount,
			endingBalance,
			Enum.AnalyticsEconomyTransactionType.Gameplay.Name,
			sku
		)
	end)
	if not success then warn("[Analytics] economia falhou:", message) end
end

function ProductionAnalytics.cleanup(player: Player)
	loggedSteps[player] = nil
end

return table.freeze(ProductionAnalytics)
  1. No script que carrega o perfil, chame passo 1 “Joined”; depois da primeira coleta confirmada, passo 2 “Collected First Coin”; depois da compra segura, passo 3 “Bought First Upgrade”; após a primeira volta, passo 4 “Completed First Loop”.
  2. Após somar moeda no servidor, chame logCoinSource com quantidade e saldo final reais. Não chame quando o cliente apenas toca numa moeda antes da validação.
  3. Em Players.PlayerRemoving, chame cleanup. Teste em staging; no Creator Dashboard → Analytics → Funnels/Economy → View Events, confirme eventos.
  4. Force uma tentativa rejeitada e confirme que nenhum evento de sucesso é gerado. Para reiniciar, use outro jogador/teste; etapas repetidas do mesmo onboarding são ignoradas. Para desfazer, remova chamadas e módulo.

Diagnóstico: evento demais indica chamada antes de sucesso ou repetição; painel vazio pode refletir experiência não publicada, atraso ou assinatura errada; nomes variados por jogador causam cardinalidade inútil. Gráficos agregados não aparecem instantaneamente.

Experimento e LiveOps com guardrails

Um experimento precisa de hipótese, variante, métrica principal, guardrails e decisão antecipada. Exemplo: “reduzir texto do tutorial aumenta conclusão do onboarding”; métrica principal: passo 4; guardrails: retenção D1, denúncias e erro do servidor não pioram. Experimentos no Creator Dashboard usam configs e audiência; não faça seu próprio sorteio sem necessidade.

LiveOps mistura correções, qualidade de vida, conteúdo e eventos. Cada atualização deve ter owner, changelog, staging, release, monitoramento e rollback. Alertas devem apontar ação: erro crítico, aumento de falha de DataStore, queda de conclusão ou heartbeat degradado.

Exercícios e plano de manutenção

Fácil

Transforme “quero mais jogadores” numa pergunta mensurável e uma decisão.

Intermediário

Adicione um sink de 50 moedas após compra validada e confira saldo final.

Desafiador

Planeje experimento de onboarding com hipótese, público, métrica, dois guardrails, duração configurada na plataforma e regra de parada.

Projeto principal: dashboard mínimo e plano de atualização com pergunta, eventos, baseline, hipótese, guardrails, rollout, rollback, responsável e decisão.

  • Cada evento responde a uma pergunta.
  • Registro sucesso depois da mutação autoritativa.
  • Não envio dados sensíveis ou cardinalidade livre.
  • Experimento possui guardrails e critério de decisão.
  • LiveOps inclui manutenção e rollback.
Gabarito comentado

Fácil: “qual porcentagem de novos jogadores conclui o primeiro ciclo?”; se a maior queda é antes da coleta, revisar orientação dessa etapa.

Intermediário: use Enum.AnalyticsEconomyFlowType.Sink, quantidade positiva 50, saldo final após débito e SKU estável como FirstUpgrade.

Desafiador: não escolha vencedor só por uma oscilação. Defina antes quando parar, qual dano bloqueia rollout e como voltar ao controle.

Avaliação de domínio · não contabilizada como capítulo

Gate de produção do Módulo 9

Avance somente quando seus fluxos críticos forem seguros, medidos e reversíveis.

Evidências obrigatórias

  1. Ameaças: apresente a matriz de loja, coleta, combate e texto, com teste hostil e falha segura.
  2. Performance: mostre baseline, perfil, mudança e repetição equivalente no dispositivo-alvo.
  3. Assets: prove owner, licença, permissão, moderação e substituto dos IDs críticos.
  4. Release: execute publicação privada e ensaio de rollback compatível com schema.
  5. Dinheiro: processe o mesmo PurchaseId duas vezes e prove uma única concessão persistente; ausência/falha permanecem pendentes.
  6. Analytics: relacione pergunta, evento, hipótese, métrica principal, guardrail e decisão.

Critérios de aprovação

  • Nenhum fluxo crítico conhecido concede valor pelo cliente.
  • Toda concessão tem fonte de verdade, registro persistente e recuperação.
  • Nenhuma falha de filtro mostra texto bruto.
  • Release possui responsável, observação e rollback ensaiado.
  • Otimização e decisão de produto usam evidência reproduzível.
  • Não há segredo, asset sem procedência ou API depreciada em código novo.
Se algum item falhar

Volte ao capítulo correspondente e corrija a evidência. “Funcionou uma vez” não é critério de produção.

Rubrica e gabarito da avaliação

Aprovado: as seis evidências são reproduzíveis por outra pessoa, o recibo repetido não duplica valor, a falha de dependência preserva estado seguro e o rollback não perde dados compatíveis.

Revisão necessária: qualquer concessão sem marcador persistente, texto bruto em fallback, asset de owner incerto, otimização sem baseline ou release sem rollback bloqueia o avanço.

Excelente: além de aprovado, cada risco tem responsável, limiar de alerta e teste de regressão.

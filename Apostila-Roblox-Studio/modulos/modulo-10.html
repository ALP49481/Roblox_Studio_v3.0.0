Você aprenderá a coordenar destinos, servidores e ferramentas externas sem confundir velocidade com durabilidade nem expor credenciais. Cada laboratório tem falhas simuladas porque sistemas distribuídos precisam ser projetados para a realidade, não apenas para o caminho feliz.

Regra central

Uma mensagem, um dado de teleporte ou uma resposta HTTP é entrada não confiável até ser validada. O servidor mantém decisões importantes e nenhuma chave aparece em Script, LocalScript, ModuleScript, interface ou repositório.

Capítulo 10.1

TeleportService, múltiplos places e servidores reservados

Conduza um grupo a uma instância reservada e trate cada tentativa como uma operação de rede que pode falhar.

Objetivos, pré-requisitos e vocabulário

Pré-requisitos: 6.3, 7.3 e 9.4. Ao terminar, você distinguirá experiência, place e servidor, configurará um destino, usará TeleportAsync no servidor, transportará apenas contexto não sensível e recuperará falhas iniciais e tardias.

Place
Um mapa executável dentro de uma experiência; uma experiência pode ter vários.
PlaceId
Número que identifica um place específico.
JobId
Identificador de uma instância de servidor em execução.
Servidor reservado
Instância acessível por um código próprio, criada para um grupo ou partida.
Teleporte
Operação que encerra a presença no servidor atual e inicia entrada em outro destino.

O mapa não é o servidor

A experiência é o produto inteiro. Cada place é um mapa publicado dentro dela. Quando jogadores entram, a plataforma executa uma cópia temporária desse place em um servidor. Dois grupos podem estar no mesmo PlaceId, mas em JobIds diferentes.

DestinoConfiguraçãoUso típico
servidor público escolhido pela plataformasem opção de instânciaentrada comum
servidor público existenteServerInstanceIdreencontro em JobId conhecido
novo servidor reservadoShouldReserveServer = truedungeon ou partida exclusiva
servidor reservado existenteReservedServerAccessCodereunir partes do mesmo grupo
Opções incompatíveis

Não combine ServerInstanceId com ShouldReserveServer ou código reservado, nem combine ShouldReserveServer com ReservedServerAccessCode. Escolha um tipo de destino.

TeleportOptions:SetTeleportData() leva contexto pequeno, visível ao cliente e não criptografado. Um nome de missão ou identificador de grupo serve; moedas, inventário, permissão e recompensa devem ser confirmados por DataStore, MemoryStore ou estado do servidor.

Prática guiada — lobby privado com cancelamento

Projeto aberto: uma cópia privada de staging chamada ExpedicaoEscala. Ela deve estar publicada, com um segundo place chamado ExpeditionTest. No Creator Dashboard, mantenha ambos privados para testes e configure o acesso de teleporte dentro da própria experiência. Copie o PlaceId do destino.

  1. No place inicial, crie Workspace → TeleportLobby (Model). Dentro, crie Parts JoinPad, CancelPad e StartPad, todas ancoradas.
  2. Dentro de cada Part, crie um ProximityPrompt chamado respectivamente JoinPrompt, CancelPrompt e StartPrompt. Ajuste ActionText para Entrar, Cancelar e Iniciar.
  3. Em ServerScriptService, crie Script GroupTeleport. Substitua somente TARGET_PLACE_ID.
GroupTeleport.server.luauScript · game → ServerScriptService → GroupTeleport · servidor · inicia com a sessão
--!strict
local Players = game:GetService("Players")
local HttpService = game:GetService("HttpService")
local TeleportService = game:GetService("TeleportService")

local TARGET_PLACE_ID = 1234567890 -- substitua pelo PlaceId do destino
local MAX_RETRIES = 3
local lobby = workspace:WaitForChild("TeleportLobby")
local joinPrompt = lobby.JoinPad:WaitForChild("JoinPrompt") :: ProximityPrompt
local cancelPrompt = lobby.CancelPad:WaitForChild("CancelPrompt") :: ProximityPrompt
local startPrompt = lobby.StartPad:WaitForChild("StartPrompt") :: ProximityPrompt
local waiting: {[Player]: boolean} = {}
local retryCount: {[Player]: number} = {}

local function setStatus(player: Player, status: string)
	player:SetAttribute("TeleportStatus", status)
end

joinPrompt.Triggered:Connect(function(player: Player)
	if player:GetAttribute("TeleportStatus") == "Teleportando" then return end
	waiting[player] = true
	setStatus(player, "Na fila")
end)

cancelPrompt.Triggered:Connect(function(player: Player)
	if player:GetAttribute("TeleportStatus") == "Teleportando" then
		setStatus(player, "Cancelamento tardio recusado")
		return
	end
	waiting[player] = nil
	setStatus(player, "Fora da fila")
end)

local function collectWaiting(): {Player}
	local group: {Player} = {}
	for player in waiting do
		if player.Parent == Players then table.insert(group, player) end
	end
	return group
end

local function startGroup(player: Player)
	if not waiting[player] then
		setStatus(player, "Entre na fila primeiro")
		return
	end
	local group = collectWaiting()
	if #group < 2 then
		setStatus(player, "Aguarde pelo menos 2 jogadores")
		return
	end

	local options = Instance.new("TeleportOptions")
	options.ShouldReserveServer = true
	options:SetTeleportData({
		partyId = HttpService:GenerateGUID(false),
		sourcePlaceId = game.PlaceId,
	}) -- contexto, nunca saldo, item ou permissão

	for _, member in group do
		waiting[member] = nil
		retryCount[member] = 0
		setStatus(member, "Teleportando")
	end
	local success, message = pcall(function()
		TeleportService:TeleportAsync(TARGET_PLACE_ID, group, options)
	end)
	if not success then
		warn("[Teleport] início falhou:", message)
		for _, member in group do
			setStatus(member, "Falhou; entre novamente")
		end
	end
end

startPrompt.Triggered:Connect(startGroup)

TeleportService.TeleportInitFailed:Connect(function(
	player: Player,
	teleportResult: Enum.TeleportResult,
	errorMessage: string,
	placeId: number,
	retryOptions: TeleportOptions
)
	if player.Parent ~= Players then return end
	local attempt = (retryCount[player] or 0) + 1
	retryCount[player] = attempt
	if attempt > MAX_RETRIES then
		setStatus(player, "Falha final; entre novamente")
		warn("[Teleport] desistiu:", teleportResult.Name, errorMessage)
		return
	end
	setStatus(player, "Tentativa " .. tostring(attempt))
	task.delay(2 ^ (attempt - 1), function()
		if player.Parent ~= Players then return end
		local ok, retryMessage = pcall(function()
			TeleportService:TeleportAsync(placeId, {player}, retryOptions)
		end)
		if not ok then warn("[Teleport] retry falhou:", retryMessage) end
	end)
end)

Players.PlayerRemoving:Connect(function(player: Player)
	waiting[player] = nil
	retryCount[player] = nil
end)

Leitura do código: waiting existe apenas no servidor atual; o prompt entrega uma instância Player já ligada ao acionador; o servidor escolhe integrantes e destino. pcall captura falha durante o início. TeleportInitFailed cobre a falha posterior e entrega novas opções que preservam o mesmo destino reservado.

  1. No place ExpeditionTest, crie ServerScriptService → DestinationArrival com o código seguinte.
  2. Publique os dois places. TeleportService não funciona em Play/Run do Studio. Abra a experiência no aplicativo Roblox com duas contas de teste autorizadas; entre na fila e inicie.
  3. Antes de iniciar, cancele uma conta: somente quem permaneceu deve ser coletado. Durante “Teleportando”, o cancelamento é recusado para não criar resultado ambíguo.
DestinationArrival.server.luauScript · destino → ServerScriptService → DestinationArrival · servidor · ao entrar no place
--!strict
local Players = game:GetService("Players")

Players.PlayerAdded:Connect(function(player: Player)
	local joinData = player:GetJoinData()
	local raw = joinData.TeleportData
	if typeof(raw) ~= "table" then
		player:SetAttribute("ArrivalContext", "Sem contexto")
		return
	end
	local partyId = raw.partyId
	local sourcePlaceId = raw.sourcePlaceId
	if typeof(partyId) ~= "string" or #partyId > 64
		or typeof(sourcePlaceId) ~= "number" or not math.isfinite(sourcePlaceId) then
		player:SetAttribute("ArrivalContext", "Contexto inválido")
		return
	end
	player:SetAttribute("ArrivalContext", "Grupo " .. partyId)
	-- partyId organiza a sessão; não concede moeda, item ou acesso.
end)

Resultado esperado: o grupo abre o place de destino na mesma instância reservada e recebe ArrivalContext. Diagnóstico: falha no Studio é a limitação esperada; PlaceId incorreto ou acesso fechado produz erro; integrantes em servidores diferentes não podem ser enviados juntos por este script; uma falha tardia deve deixar o jogador no lobby com status de tentativa. Para reiniciar, reabra o lobby; para desfazer, apague apenas TeleportLobby e os dois scripts.

Teste parcial, falha e segurança

Não existe “teleporte atômico de grupo”: alguns jogadores podem chegar e outros falhar. O destino precisa tolerar chegada parcial, abandono e repetição. Para estado importante, grave um ticket curto no servidor antes de mover o grupo e reconcilie no destino. Não use TeleportData como prova de pagamento.

APIs antigas

Teleport, TeleportPartyAsync, TeleportToPlaceInstance e TeleportToPrivateServer estão depreciadas para código novo. Use TeleportAsync com TeleportOptions.

Exercícios e projeto

Fácil

Explique com exemplos a diferença entre PlaceId e JobId.

Intermediário

Adicione limite de quatro integrantes e recuse a quinta entrada com status claro.

Desafiador

Desenhe a reconciliação quando dois integrantes chegam e dois falham: timeout, retorno seguro e nenhuma recompensa duplicada.

Projeto do capítulo: lobby privado com entrada, cancelamento seguro, partida reservada, contexto não sensível e recuperação limitada. Registre num roteiro em quais estados o jogador pode cancelar.

  • Distingo experiência, place, servidor, PlaceId e JobId.
  • Chamo TeleportAsync somente no servidor.
  • Não misturo propriedades incompatíveis de TeleportOptions.
  • Uso pcall e TeleportInitFailed.
  • Valido TeleportData e não concedo valor por ela.
  • Testo teleporte real no aplicativo Roblox publicado.
Gabarito comentado

Fácil: PlaceId identifica o mapa publicado; JobId identifica uma execução temporária dele. Reiniciar um servidor muda o JobId, não o PlaceId.

Intermediário: conte collectWaiting() antes de inserir. A quinta pessoa permanece fora e recebe “Grupo cheio”. O limite é decidido no servidor.

Desafiador: uma solução válida cria um ticket idempotente por partida, marca quem chegou, espera um prazo e retorna os presentes ao lobby se o mínimo não for atingido. Recompensa só é concedida depois do estado confirmado e com marcador persistente.

Capítulo 10.2

MemoryStore, MessagingService e matchmaking

Coordene servidores com dados temporários, aceite entrega imperfeita e projete recuperação antes da escala.

Objetivos, pré-requisitos e vocabulário

Pré-requisitos: 7.3, 8.1 e 10.1. Você escolherá entre DataStore e MemoryStore, usará fila e mapa temporários, tratará expiração e invisibilidade, explicará mensagens de melhor esforço e simulará uma fila 2v2 com abandono.

TTL
Tempo de vida; após ele, o dado temporário expira.
Fila
Estrutura em que itens aguardam processamento por ordem/prioridade.
Invisibility timeout
Período em que um item lido fica oculto de outros leitores antes de reaparecer.
Best effort
Entrega tentada, mas sem garantia absoluta.
Reconciliação
Consulta ao estado verdadeiro para corrigir mensagem perdida, repetida ou atrasada.

Escolha pelo tempo de vida

NecessidadeServiçoExemplo
sobreviver a sessõesDataStoremoedas, inventário, progresso
temporário e compartilhado entre servidoresMemoryStorefila de partida, lock, presença curta
avisar outros servidores rapidamenteMessagingService“partida encontrada”; não é prova única
temporário em um único servidortabela Luaucooldown, estado da rodada local

MemoryStore oferece hash map para chave direta, sorted map para ordenação e queue para processamento. Tudo expira: remova itens concluídos, use TTL curto, envolva chamadas em pcall e respeite quotas compartilhadas pela experiência.

Na fila, ReadAsync devolve itens e um identificador de leitura. Esses itens ficam invisíveis pelo prazo configurado. Só depois de concluir o passo correspondente você chama RemoveAsync; se o worker morrer antes, os itens reaparecem.

Mensagem não é estado

MessagingService normalmente é rápido, mas é de melhor esforço. Uma mensagem pode atrasar ou não chegar. Grave a atribuição temporária e permita que o servidor consulte essa atribuição: a mensagem apenas acelera a descoberta.

Prática guiada — laboratório 2v2

Escopo honesto: este laboratório forma grupos de quatro jogadores no mesmo lobby e usa MemoryStore para observar as APIs e falhas. Ele não é um matchmaking distribuído completo. Para produção com jogadores em servidores diferentes, acrescente claim atômico, atribuição por usuário, servidor reservado, notificação e reconciliação.

Projeto aberto: place inicial de ExpedicaoEscala. Ative Studio → Game Settings → Security → Enable Studio Access to API Services apenas numa versão de teste. Nunca aponte esse teste para dados de produção.

  1. Crie Workspace → MatchmakingLab (Model), Parts ancoradas JoinQueue e CancelQueue.
  2. Em cada Part, crie ProximityPrompt chamado JoinPrompt e CancelPrompt.
  3. Em ServerScriptService, crie Script MatchmakingLab. Primeiro use SIMULATE_SERVER_START_FAILURE = true.
MatchmakingLab.server.luauScript · game → ServerScriptService → MatchmakingLab · servidor · inicia com a sessão
--!strict
local Players = game:GetService("Players")
local HttpService = game:GetService("HttpService")
local MemoryStoreService = game:GetService("MemoryStoreService")
local MessagingService = game:GetService("MessagingService")

local TICKET_TTL = 45
local INVISIBILITY_TIMEOUT = 8
local SIMULATE_SERVER_START_FAILURE = true
local queue = MemoryStoreService:GetQueue("MatchQueue2v2V1", INVISIBILITY_TIMEOUT)
local tickets = MemoryStoreService:GetHashMap("MatchTickets2v2V1")
local assignments = MemoryStoreService:GetHashMap("MatchAssignments2v2V1")
local lab = workspace:WaitForChild("MatchmakingLab")
local joinPrompt = lab.JoinQueue:WaitForChild("JoinPrompt") :: ProximityPrompt
local cancelPrompt = lab.CancelQueue:WaitForChild("CancelPrompt") :: ProximityPrompt
local localTokens: {[Player]: string} = {}
local processing = false

local function key(userId: number): string
	return "user:" .. tostring(userId)
end

local function setStatus(player: Player, value: string)
	player:SetAttribute("MatchStatus", value)
end

local function join(player: Player)
	if localTokens[player] then
		setStatus(player, "Já está na fila")
		return
	end
	local token = HttpService:GenerateGUID(false)
	local ticket = {userId = player.UserId, token = token, jobId = game.JobId}
	local ok, message = pcall(function()
		tickets:SetAsync(key(player.UserId), ticket, TICKET_TTL)
		queue:AddAsync(ticket, TICKET_TTL, 0)
	end)
	if not ok then
		warn("[Match] entrada falhou:", message)
		setStatus(player, "Serviço indisponível; tente depois")
		return
	end
	localTokens[player] = token
	setStatus(player, "Procurando partida")
end

local function cancel(player: Player)
	local token = localTokens[player]
	if not token then
		setStatus(player, "Não estava na fila")
		return
	end
	local ok, message = pcall(function()
		tickets:RemoveAsync(key(player.UserId))
	end)
	if not ok then
		warn("[Match] cancelamento inconclusivo:", message)
		setStatus(player, "Cancelamento inconclusivo; aguarde o TTL")
		return
	end
	localTokens[player] = nil
	setStatus(player, "Fila cancelada")
	-- O item da queue expira; o mapa invalida seu token imediatamente.
end

local function currentTicket(candidate: any): boolean
	if typeof(candidate) ~= "table" or typeof(candidate.userId) ~= "number"
		or typeof(candidate.token) ~= "string" or typeof(candidate.jobId) ~= "string" then
		return false
	end
	local stored = tickets:GetAsync(key(candidate.userId))
	return typeof(stored) == "table" and stored.token == candidate.token
end

local function tryFormMatch()
	if processing then return end
	processing = true
	local ok, message = pcall(function()
		local items, readId = queue:ReadAsync(4, true, 2)
		if #items ~= 4 then return end
		local seen: {[number]: boolean} = {}
		for _, candidate in items do
			if not currentTicket(candidate) or seen[candidate.userId] then
				return -- itens reaparecem depois da invisibilidade
			end
			seen[candidate.userId] = true
		end

		if SIMULATE_SERVER_START_FAILURE then
			warn("[Match] falha simulada; itens não removidos e voltarão à fila")
			return
		end

		local matchId = HttpService:GenerateGUID(false)
		for index, candidate in items do
			assignments:SetAsync(key(candidate.userId), {
				matchId = matchId,
				team = if index <= 2 then "Azul" else "Laranja",
			}, 30)
		end
		queue:RemoveAsync(readId)
		for _, candidate in items do
			tickets:RemoveAsync(key(candidate.userId))
			MessagingService:PublishAsync("match:" .. candidate.jobId, {
				userId = candidate.userId,
				matchId = matchId,
			}) -- aviso rápido; assignments é a reconciliação
		end
	end)
	if not ok then warn("[Match] worker falhou:", message) end
	processing = false
end

local function applyAssignment(player: Player)
	local ok, assignment = pcall(function()
		return assignments:GetAsync(key(player.UserId))
	end)
	if ok and typeof(assignment) == "table"
		and typeof(assignment.matchId) == "string"
		and (assignment.team == "Azul" or assignment.team == "Laranja") then
		localTokens[player] = nil
		setStatus(player, "Partida " .. assignment.matchId .. " · " .. assignment.team)
	end
end

local connection = MessagingService:SubscribeAsync("match:" .. game.JobId, function(message)
	local data = message.Data
	if typeof(data) ~= "table" or typeof(data.userId) ~= "number" then return end
	local player = Players:GetPlayerByUserId(data.userId)
	if player then applyAssignment(player) end
end)

joinPrompt.Triggered:Connect(join)
cancelPrompt.Triggered:Connect(cancel)
Players.PlayerRemoving:Connect(function(player)
	cancel(player)
end)

task.spawn(function()
	while task.wait(3) do
		tryFormMatch()
		for _, player in Players:GetPlayers() do applyAssignment(player) end
	end
end)

game:BindToClose(function()
	connection:Disconnect()
end)

Leitura: cada ticket recebe token imprevisível e TTL. Cancelar remove o registro atual do hash map; uma cópia antiga na fila deixa de ser válida. A leitura fica invisível por oito segundos; falha simulada não remove o lote, então ele volta. A atribuição é gravada antes da mensagem. O polling de applyAssignment reconcilia avisos perdidos.

  1. Use Test → Start com quatro clientes. Acione JoinPrompt em todos. Com falha simulada, o Output deve avisar e os status devem continuar procurando.
  2. Pare, altere a constante para false e repita. Os quatro devem receber o mesmo MatchId e dois jogadores por equipe.
  3. Repita com três jogadores e depois com quatro, cancelando um antes do processamento. O ticket cancelado não pode receber atribuição.
  4. Para inspecionar, use Creator Dashboard → Data Stores → Memory Stores/Observability quando disponível. Para reiniciar limpo, troque o sufixo V1 por V2; para desfazer, remova Model e Script.

Erros comuns: “API Services rejected request” indica acesso de teste desativado; limite excedido pede menos chamadas e backoff; quatro cópias do mesmo usuário não formam grupo por causa de seen; a assinatura de mensagem pode falhar e deve ser tratada com pcall em produção. O código é um laboratório didático: a escrita sequencial de quatro assignments ainda pode falhar no meio.

Do laboratório ao distribuído

Roblox também possui matchmaking de plataforma: ele filtra servidores elegíveis e os pontua com sinais. Uma fila própria de gameplay é outra arquitetura. Para evoluir este laboratório, escolha um coordenador com lease, faça claim atômico por usuário, crie o servidor reservado, grave uma atribuição idempotente, avise os servidores de origem e deixe cada origem teleportar seus jogadores locais. Se o destino não iniciar, expire a atribuição e recoloque o usuário com uma nova tentativa.

FalhaDetecçãoRecuperação
jogador abandonaticket atual ausente/token mudouignorar item antigo; TTL limpa
worker cai após leiturainvisibility timeout terminaitem reaparece
mensagem somepoll da assignmentreconciliação encontra estado
destino não iniciaassignment/heartbeat expiraretornar à fila com novo ticket
quotaerro + observabilidadebackoff, lote, sharding e menos payload

Exercícios e projeto

Fácil

Classifique moeda, fila, aviso de partida e cooldown entre DataStore, MemoryStore, MessagingService e tabela Luau.

Intermediário

Adicione ao ticket uma faixa de habilidade inteira entre 0 e 100 e rejeite tipo/valor inválido no worker.

Desafiador

Desenhe o protocolo distribuído completo com claim, assignment, reserved server, mensagem, polling, timeout e idempotência.

Projeto do capítulo: fila 2v2 observável com cancelamento, TTL, falha simulada, assignment temporária e reconciliação. Entregue também um diagrama de estados: fora → procurando → atribuído → iniciado/expirado.

  • Persistência usa DataStore; coordenação temporária usa MemoryStore.
  • Entendo TTL, invisibilidade, leitura e remoção.
  • Toda chamada de nuvem pode falhar.
  • Mensagem acelera, mas não substitui estado consultável.
  • Não confundo fila própria com matchmaking padrão da plataforma.
  • Sei explicar o limite didático do laboratório.
Gabarito comentado

Fácil: moeda: DataStore; fila: MemoryStoreQueue; aviso: MessagingService; cooldown local: tabela Luau. Assignment curta cabe em MemoryStoreHashMap.

Intermediário: valide typeof(skill) == "number", math.isfinite(skill), inteiro e faixa. O servidor calcula a habilidade; não aceite a pontuação declarada pelo cliente.

Desafiador: o protocolo correto grava antes de avisar, usa um identificador estável da operação e permite polling. Se qualquer etapa fica inconclusiva, o mesmo ID não pode criar duas partidas nem duas recompensas. Há mais de uma solução válida; documente consistência e rollback.

Capítulo 10.3

Open Cloud, autenticação e automação externa

Separe código da Engine, requisições do servidor e ferramentas externas; conceda só a permissão necessária.

Objetivos, pré-requisitos e vocabulário

Pré-requisitos: 9.1, 9.4, 9.6 e introdução a HTTP. Você distinguirá três superfícies de API, configurará um segredo sem escrevê-lo no código, fará leitura fixa no servidor, validará resposta e projetará uma automação externa com menor privilégio.

REST API

Open Cloud é um conjunto de APIs REST. Uma automação no Render, numa pipeline ou num computador não está dentro da sessão Roblox: ela autentica diretamente e continua existindo mesmo sem servidor de jogo. Um Script com HttpService roda dentro de cada servidor e compartilha seus limites. Ele alcança sites HTTPS permitidos e somente os endpoints Open Cloud explicitamente marcados com suporte a HttpService.

“É Open Cloud” não significa “pode chamar do jogo”

Abra a referência do endpoint e procure o selo HttpService. A lista muda; valide novamente antes de implementar. Nunca use o jogo como proxy para uma URL escolhida pelo cliente.

Segredo, autenticação e escopo

Para uma automação sob seu controle, API key costuma ser o começo mais simples. Para um aplicativo de terceiros agir em nome de cada usuário com consentimento, use OAuth 2.0 quando o endpoint e o cenário suportarem. Em ambos os casos, selecione o recurso exato, apenas leitura ou escrita necessária, expiração e rotação.

  1. No Creator Dashboard, crie uma API key dedicada ao laboratório, limitada somente à experiência e à permissão de leitura exigida por Get Universe. Não reutilize uma chave administrativa.
  2. Na experiência, abra Creator Dashboard → Secrets e crie OPEN_CLOUD_READ_KEY. Cole o valor apenas no campo secreto e limite o domínio aplicável a apis.roblox.com.
  3. Para teste colaborativo/live, use o Secrets Store. Para teste local, configure Local Secrets em Studio → Experience Settings → Security. Não envie esse arquivo/valor a ninguém.
  4. Ative Studio → File → Experience Settings → Security → Allow HTTP Requests somente no ambiente de laboratório.
Nunca faça isto

Não escreva a chave em Script, ModuleScript, ReplicatedStorage, DataStore, HTML, Aiven, log, print, screenshot ou Git. No Render, credenciais externas ficam em variáveis secretas do serviço e nunca no JavaScript enviado ao navegador.

Prática guiada A — leitura no servidor da experiência

Projeto aberto: ExpedicaoEscala em staging. Em ServerScriptService, crie Script OpenCloudReadLab. O endereço é fixo; jogador nenhum escolhe rota, método ou cabeçalho.

OpenCloudReadLab.server.luauScript · game → ServerScriptService → OpenCloudReadLab · servidor · uma leitura na inicialização
--!strict
local HttpService = game:GetService("HttpService")

local MAX_ATTEMPTS = 3
local universeId = tostring(game.GameId)
local url = "https://apis.roblox.com/cloud/v2/universes/" .. universeId

local function requestUniverse(): ({[string]: any}?, string?)
	for attempt = 1, MAX_ATTEMPTS do
		local ok, response = pcall(function()
			return HttpService:RequestAsync({
				Url = url,
				Method = "GET",
				Headers = {
					["x-api-key"] = HttpService:GetSecret("OPEN_CLOUD_READ_KEY"),
					["content-type"] = "application/json",
				},
			})
		end)
		if not ok then
			if attempt == MAX_ATTEMPTS then return nil, "falha de rede" end
			task.wait(2 ^ (attempt - 1))
			continue
		end
		if response.Success and response.StatusCode == 200 then
			local decodedOk, data = pcall(function()
				return HttpService:JSONDecode(response.Body)
			end)
			if not decodedOk or typeof(data) ~= "table" then
				return nil, "JSON inválido"
			end
			if typeof(data.path) ~= "string" or #data.path > 200 then
				return nil, "resposta fora do contrato"
			end
			return data, nil
		end
		if response.StatusCode ~= 429 and response.StatusCode >= 400
			and response.StatusCode < 500 then
			return nil, "pedido recusado: " .. tostring(response.StatusCode)
		end
		if attempt < MAX_ATTEMPTS then task.wait(2 ^ (attempt - 1)) end
	end
	return nil, "serviço indisponível"
end

local universe, problem = requestUniverse()
if universe then
	print("Open Cloud validado para:", universe.path)
else
	warn("[OpenCloud]", problem) -- não imprime header, chave ou body
end

Leitura: GetSecret() retorna um objeto secreto utilizável no header, não uma string para exibição. RequestAsync() retorna sucesso HTTP, status, headers e body; rede bem-sucedida não significa resposta válida. O código limita tentativas, distingue 4xx permanente de 429/5xx e valida o JSON mínimo.

  1. Execute em staging colaborativo/live. No Output, espere Open Cloud validado para: seguido do caminho do universo.
  2. Renomeie temporariamente o segredo para simular ausência: o sistema deve exibir apenas falha de rede, nunca a credencial. Restaure.
  3. Troque o endpoint temporariamente por uma rota inexistente: espere recusa 404 sem retry infinito. Restaure antes de salvar.
  4. Para reiniciar, Stop/Play; para desfazer, apague o Script, remova o segredo de laboratório e revogue a API key no Creator Dashboard.

Diagnóstico: erro de HTTP desativado pede a configuração Security; 401/403 indica credencial, escopo ou recurso; 429 pede aguardar/reduzir; 5xx pede retry limitado; JSON inválido ou contrato inesperado deve falhar fechado. Não imprima response.Body indiscriminadamente.

Prática guiada B — automação externa no Render

A aplicação da apostila já usa Render e Aiven, mas a chave Roblox não pertence ao banco nem ao frontend. Um worker/rota administrativa no servidor lê uma variável secreta configurada no painel do Render. O exemplo abaixo é apenas uma requisição manual externa e não contém credencial.

Consulta externa (PowerShell)Terminal local autorizado · fora do Roblox · variável de ambiente temporária
$headers = @{ "x-api-key" = $env:ROBLOX_OPEN_CLOUD_KEY }
$universeId = "SUBSTITUA_PELO_UNIVERSE_ID"
Invoke-RestMethod `
  -Method Get `
  -Uri "https://apis.roblox.com/cloud/v2/universes/$universeId" `
  -Headers $headers
  1. Defina ROBLOX_OPEN_CLOUD_KEY apenas na sessão do terminal ou no cofre de segredos do Render; não salve no histórico, arquivo ou repositório.
  2. Use uma chave separada daquela do jogo. Restrinja-a ao universo e à leitura.
  3. Confirme o ID e execute. Valide status e campos antes de alimentar qualquer automação.
  4. Apague a variável ao terminar e revogue a chave de laboratório. Em produção, registre código de status, latência e ID da operação — nunca a credencial.

Automação externa é a escolha natural para publicação, relatório agendado e integração administrativa. Servidor da experiência é apropriado para uma leitura necessária durante a sessão e explicitamente permitida. Aiven guarda o progresso da apostila; ele não é cofre de chave Open Cloud.

Limites, respostas e webhooks

Prepare-se para 401/403, 404, 409, 429, timeout e 5xx. Em 429, respeite retry-after quando disponível; caso contrário, use backoff exponencial com limite. API keys compartilham limites por owner, OAuth possui limites por token e chamadas dentro do jogo também consomem o limite HTTP do servidor. Faça lotes quando o endpoint permitir.

Para webhooks, confirme a autenticação/assinatura definida pela documentação do produto, limite o tamanho, valide content-type e schema, use ID de evento para idempotência e responda rapidamente. Um webhook pode repetir. Uma página web pública nunca recebe segredo de servidor.

Exercícios e projeto

Fácil

Classifique cinco ações como Engine API, HttpService no jogo ou automação externa.

Intermediário

Acrescente jitter ao backoff e trate retry-after sem criar espera ilimitada.

Desafiador

Modele uma automação de publicação e uma consulta permitida no jogo: ator, credencial, escopo, recurso, rotação, limites, schema, idempotência, logs e revogação.

Projeto do capítulo: documento de ameaça e execução para duas rotas: leitura externa no Render e leitura fixa do servidor Roblox. Inclua diagrama, chave separada, menor privilégio, teste de falhas, resposta inválida e procedimento de revogação.

  • Separo Engine API, HttpService e Open Cloud.
  • Verifico o selo HttpService no endpoint exato.
  • Nenhuma credencial aparece em código, frontend, banco ou log.
  • Uso Secrets Store/GetSecret() no servidor Roblox.
  • Escolho API key ou OAuth conforme o ator.
  • Valido status, JSON, schema e limites.
  • Falha e repetição produzem resultado seguro e idempotente.
Gabarito comentado

Fácil: mover Player: Engine; consultar serviço externo durante a sessão: HttpService no servidor; publicar place em pipeline: Open Cloud externo; botão local: Engine/client; relatório noturno: automação externa.

Intermediário: limite o atraso máximo, prefira retry-after válido e some pequena aleatoriedade. Cancele após poucas tentativas; retry infinito multiplica uma pane.

Desafiador: publicação pede worker externo e escopo de escrita apenas no place necessário; leitura em jogo pede endpoint com selo HttpService, segredo restrito a apis.roblox.com, rota fixa, baixa frequência e fallback. Credenciais devem ser diferentes e revogáveis. Há outras soluções válidas.
